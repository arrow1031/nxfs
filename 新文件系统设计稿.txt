## 一、总体架构

### 1.1 模块划分

| 模块 | 运行位置 | 职责 | 许可证 |
| :--- | :--- | :--- | :--- |
| **翻译层** | 内核态/用户态 | API请求 ↔ 文件系统指令双向转译，不做策略 | Apache 2.0 |
| **存储抽象层** | 用户态进程 | 块读写、校验和、设备管理、NAND缓存管理（⏸️ NAND 部分属二期，冻结） | 可闭源 |
| **元数据引擎** | 用户态进程 | CoW、事务、日志、快照、子卷 | 可闭源 |
| **功能模块层** | 用户态进程 | 压缩、加密、RAID、去重 | 可闭源 |
| **Windows集成层** | WinFsp/Dokany | IRP翻译、挂载、缓存 | 保持原许可证 |
| **EFI驱动** | UEFI固件环境 | 只读引导，直接加载内核 | BSD兼容 |
| **NAND缓存层** | 用户态进程 | 可选，在NAND上创建特殊文件作为缓存容器（⏸️ **属二期，整体冻结**） | 可闭源 |
| **SSD优化层** | 用户态进程 | 语义化放置、写放大优化（暂缓，内部探索） | 暂不发布 |

### 1.2 通信机制

- 模块间通过 **C ABI + IPC** 通信，进程隔离。
- 热路径走**共享内存 + 批量提交**，避免逐操作IPC。
- 日志批量下放，不逐条写盘。
- 翻译层只做转译，不做策略判断。


## 二、磁盘格式与物理布局

### 2.1 分区结构

```
┌─────────────────────────────────────────┐
│ LBA 0: MBR / GPT 头部                    │  ← 操作系统和分区工具认这里
├─────────────────────────────────────────┤
│ 分区起始: 兼容区（32-64MB）               │  ← 引导加载器 + 引导配置
├─────────────────────────────────────────┤
│ 主总账（64KB-256KB）                     │  ← 文件系统权威状态源
│ 副总账（分区中部，同主总账）               │
│ 跨文件区（256MB-1GB）                    │
│ 数据区（文件夹块、文件数据、日志区）        │
└─────────────────────────────────────────┘
```

### 2.2 簇与偏移

- 簇大小：4KB（可配置为16KB/64KB）。
- 偏移以簇号记录：4字节簇号 + 2字节长度 + 1字节状态 + 1字节校验 = 8字节/条。
- 每簇头部带 CRC32C 校验和，CPU 计算，存储层只搬簇。

### 2.3 总账结构

| 字段 | 内容 |
| :--- | :--- |
| 分区标识 | 文件系统类型 GUID、版本号、簇大小 |
| 全局事务状态 | 当前事务 ID、检查点位置、日志区总量 |
| 跨文件区指针 | 起始簇号、大小、写入指针、检查点位置 |
| 文件夹日志树根 | 根文件夹日志区偏移、摘要状态 |
| **引导文件表** | 内核文件 LBA、大小、校验和（4个条目） |
| 校验和 | 整个总账的 CRC32C |

**副本地址自描述，推导规则只有一个实现点**（v0.6.2 补充；依据实现仓既有事实，非新设计）

总账的两个副本、以及引导文件表的两个副本，**地址都写在总账里**：

| 地址 | 来源 |
| :--- | :--- |
| 主总账 | 常量 `NXFS_LAYOUT_LEDGER_PRIMARY_LBA`（分区头固定位置，不是推导值） |
| **副总账** | **自描述**：`nxfs_disk_ledger_t::secondary_lba`＝容量中点向下对齐 1024 扇区 |
| 引导文件表（主 / 副） | 同为自描述：`boot_table_lba` / `boot_table_backup_lba` |

三条纪律：

1. **一条布局规则只有一个实现点**，且必须在规则的**所有者**手里（磁盘布局＝包 20 的
   `nxfs_disk_layout.h`）。消费者**只调用，不重写公式**——哪怕写出来"一字不差"。
2. **盘上自描述值优先于现场推导**：挂载路径读到什么就是什么；现场推导只在**没有总账可读**
   的场合使用（格式化）。这样"镜像搬家 / 布局演进"是可被发现的事实，而不是各层各算一套、
   悄悄读到不同扇区却谁都不报错。
3. **测试侧故意独立复算是允许且鼓励的**（能抓住实现与常量的漂移），但必须注释写明
   "故意独立复算"，且不计为实现侧的实现点。

> 本条不是新机制，而是把**已存在的事实**写成规范并消灭重复：盘上结构从 v1 起就自描述
> 这三个地址，但兼容层解析时只上报其中一部分，迫使元数据引擎自己重算。
> 已知重写点与消除计划登记在 `NXFS开发包/10-公共约定.md` §14.4。

### 2.4 分区表兼容

> ⚠️ **已修正（v0.6.1）** —— 原稿的两个取值均与既有事实冲突，已换为经权威表核实的值。

- MBR 用**自定义类型字节 `0x7F`**，GPT 用**自定义 GUID `13073c46-c0da-4696-817f-6d12902515e3`**。
- 操作系统看到后**不自动挂载、不自动格式化**。
- 分区表只描述分区起止 LBA，不描述内部结构。

**为什么要修正（原取值的问题）**：

| 项 | 原稿取值 | 问题 |
| :--- | :--- | :--- |
| MBR 类型字节 | `0x8E` | **已被占用 = Linux LVM**。会让 Linux 侧 `blkid`/`lsblk`/`systemd` 的 LVM 探测把它误认为 LVM 物理卷，可能触发自动激活尝试——与"不自动挂载"的目标直接相悖 |
| GPT 类型 GUID | Microsoft 基本数据 | 正是"会被 Windows 自动挂载并**提示格式化**"的那个 GUID。用户误点"格式化"即造成数据丢失 |

**取证依据**：util-linux 2.42.3 官方源码
`include/pt-mbr-partnames.h`（该表已分配 101 个 MBR 类型字节）、
`include/pt-gpt-partnames.h`（已分配 224 个 GPT 类型 GUID）。

**为什么选 `0x7F`**：该值在权威表中**完全未出现**，且是 `0x80` 密集分配块之前的
最后一个未分配值（`0x70` DiskSecure Multi-Boot / `0x75` PC/IX / `0x80` Old Minix）。
它刻意排在 `0x80`–`0x8E` 这段 Linux 系统类型区间**之前**。

**为什么 GPT 用随机 v4**：GUID 空间 128 位，无需查表即可避免冲突；随机生成后
与权威表 224 个已知 GUID 比对无冲突。Windows 对未知 GUID 的分区默认不自动挂载、
不提示格式化——这正是自定义 GUID 能达到目标的原因。

**复核方式**：`NXFS开发包` 目录外的 API 仓库中提供 `verify/select_ids.py`，
可打印全部 155 个未分配 MBR 类型字节，便于改选其他值。


## 三、三层日志体系

### 3.1 层级职责

| 层级 | 记录内容 | 日志量（1000文件夹） |
| :--- | :--- | :--- |
| **顶层（根层）** | 子文件夹物理偏移 + 摘要标记 + **簇级操作** | ~64KB |
| **中间层** | 子文件夹偏移 + **文件夹级操作** | ~3.2MB |
| **底层** | **文件级操作**（inode变更、文件与簇映射） | ~115MB |

### 3.2 日志树与物理偏移

- 父文件夹日志记录子文件夹的**物理偏移（簇号）**。
- 每个日志区头部带**自验证标识**（文件夹ID + 版本号 + 校验和）。
- 恢复时从根逐层向下，每层读一个头簇（4KB），定位跳转。
- 偏移记录按簇对齐。

### 3.3 分层详略

| 层级 | 日志详略 | 优化策略 |
| :--- | :--- | :--- |
| 顶层 | 只记"当前状态"，不保留历史 | 每小时优化一次 |
| 中间层 | 文件夹级操作 + 摘要 | 检查点后回收 |
| 底层 | 完整文件级事务 | 检查点后回收 |

### 3.4 父日志条目结构

| 字段 | 大小 | 内容 |
| :--- | :--- | :--- |
| 子文件夹偏移 | 4字节 | 簇号 |
| 长度 | 2字节 | 日志区大小 |
| 状态 | 1字节 | 正常/迁移中/待回收/待变更 |
| 类型标记 | 1字节 | 普通/程序 |
| 校验 | 1字节 | 条目校验 |

### 3.5 日志区隔离

- 每个子文件夹日志区按独立extent分配。
- 日志区之间预留至少1簇隔离带。
- 物理距离尽量远（外圈/中圈/内圈分布）。
- 恢复时按物理区域分片扫描。


## 四、跨文件区

### 4.1 工作流

| 动作步 | 动作 | 状态标记 |
| :--- | :--- | :--- |
| 操作发生 | 日志写入跨文件区 | 待分发 |
| 后台分发 | 跨文件区 → 文件夹日志区 | 分发中 |
| 分发完成 | 目标日志区确认接收 | 转移完成 |
| 总区回收 | 后台批量清除 | 无 |

- 跨文件操作即时写入跨文件区，回报用户，后台空闲时分发。
- 分发操作本身留痕，哪个文件分发完成就抹除哪个转译条目。
- 分发按文件夹聚合，一次性顺序写入。

### 4.2 恢复逻辑

| 跨文件区状态 | 文件夹日志状态 | 恢复动作 |
| :--- | :--- | :--- |
| 无条目 | 无条目 | 跳过 |
| 待分发 | 无条目 | 重新分发 |
| 分发中 | 有条目 | 继续完成分发 |
| 转移完成 | 有条目 | 跳过，等待回收 |
| 分发中 | 无条目 | 回滚分发标记 |


## 五、文件夹块与写入策略

### 5.1 块结构

```
[日志区][文件A数据+预留][间隔][文件B数据+预留][间隔][文件C数据+预留][日志区]
```

- 预留量：小文件64KB-256KB，中文件10%-20%，大文件5%-10%。
- 间隔：1-2簇缓冲带，吸收文件增长。
- 封块：日志区达阈值或子文件夹数超限时封块。

### 5.2 增长处理

| 增长程度 | 动作 |
| :--- | :--- |
| 预留内 | 就地扩展，更新元数据 |
| 用完预留，间隔够 | 占用间隔 |
| 间隔不够 | 块内迁移或拆extent |

### 5.3 压缩时回收预留

- 触发：预留浪费率 > 30%。
- 动作：压缩古旧文件预留，空间归还块空闲池。
- 古旧定义：>6个月未修改 + 预留使用率<20%。


## 六、程序文件夹优化

### 6.1 文件夹级程序标记

- 程序文件夹作为文件夹级属性，标记在父日志条目里。
- 翻译层读取子文件夹偏移时，同一簇内顺手拿到类型标记。
- 传播规则：程序文件夹下的子文件夹默认继承，可显式覆盖。

### 6.2 程序块内部分区

```
[日志区][程序文件区（只读为主）][写区（日志/存档/配置）][日志区]
```

- 程序文件区：exe、DLL、资源，紧凑排列。
- 写区：游戏运行时的日志、存档、配置，按普通块规则管理。
- 大文件（>64MB）独立成块，连续区域，一次寻道读取。

### 6.3 读路径分级

| 路径 | 适用 | 流程 | 延迟 |
| :--- | :--- | :--- | :--- |
| 热路径 | 程序块内文件，已缓存元数据 | 翻译层直接读块 → 校验和验证 → 返回 | 寻道 + 微秒级 |
| 普通路径 | 非程序文件，或未缓存元数据 | 翻译层 → 用户态模块 → 读块 → 校验和验证 → 返回 | 寻道 + 0.5-2ms |

### 6.4 元数据热缓存旁路

- 翻译层维护只读元数据缓存。
- 命中：翻译层直接返回，微秒级。
- 失效：用户态模块批量通知翻译层失效。
- 缓存只缓存已提交事务的元数据。

### 6.5 文件类型识别（三层）

| 层级 | 规则 | 处理 |
| :--- | :--- | :--- |
| 第一层 | 扩展名 + 文件头一致 | 按对应类型处理 |
| 第二层 | 扩展名与文件头不一致 | 按文件头处理 |
| 第三层 | 无法识别 | 按普通文件处理 |
| 用户显式标记 | 覆盖自动识别 | 指定程序目录 |


## 七、删除与回收

### 7.1 文件夹删除

| 步骤 | 动作 |
| :--- | :--- |
| 即时 | 父日志标记"子树X待删除"，回报用户 |
| 后台渗透 | 逐层向下标记，按文件夹批量回收 |
| 空间回收 | 顶层extent整块蒸发，按extent批量释放 |

### 7.2 块级蒸发

- 文件夹及其内容视为复合分配单元。
- 顶层extent按文件夹聚合，删除时整块标记"待回收"。
- 后台按extent顺序扫描，批量更新空闲位图。
- 空间回收参照文件系统删除大文件的机制。

### 7.3 延迟释放

- 被标记待删除的簇，状态为"延迟释放"。
- 新写入优先使用真正空闲的簇。
- 系统保留5%紧急空闲空间。


## 八、碎片整理

### 8.1 迁移即整理

- 从其他文件系统迁入时，目标盘自上而下构建。
- 文件夹分配连续区域，文件按源顺序写入。
- 迁入完成后天然紧凑，无需整理。

### 8.2 块级整理

| 触发条件 | 动作 |
| :--- | :--- |
| 块内碎片率 > 阈值 | 选定块，找连续空闲区域 |
| 系统空闲 + 空间压力低 | 顺序写入新区域 |
| 写入热点集中 | 更新父日志偏移，旧块标记待回收 |

- 整理时锁定块，新写入路由到新块。
- 与压缩协同：压缩后数据变小，可原地重写或迁移到更小连续区域。


## 九、恢复机制

### 9.1 恢复层级

| 层级 | 位置 | 恢复速度 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 主总账 | 分区头 | 毫秒级 | 正常挂载 |
| 副总账 | 分区中部 | 秒级 | 主总账损坏 |
| 碎片区备份 | 碎片区 | 30分钟-1.5小时 | 前两级都损坏 |
| 文件夹日志区 | 各文件夹内 | 中 | 按日志重放 |

### 9.2 恢复时间

| 场景 | 预计时间 |
| :--- | :--- |
| 正常挂载 | 毫秒级 |
| 主总账损坏，副总账恢复 | 秒级 |
| 断电后少量日志重放 | 10-60秒 |
| 中等规模重放（检查点30-60分钟） | **1-3分钟** |
| 大量文件夹同时修改 | 10-20分钟 |
| 极端恢复（碎片备份） | 30分钟-1.5小时 |

### 9.3 检查点策略

- 间隔：30-60分钟。
- 日志区总量上限：分区容量1%。
- 超过上限强制检查点。
- 检查点按树形层级自上而下推进。


## 十、升层与降层

### 10.1 延迟升层

| 事件 | 动作 |
| :--- | :--- |
| 底层文件夹创建首个子文件夹 | 父日志标记"待变更" |
| 首次在子文件夹中创建文件 | 落实升层：分配中间层日志区 |
| 从未在子文件夹中创建文件 | 保持"待变更"，不消耗额外空间 |

### 10.2 降层

- 所有子文件夹删除后，日志区头部格式标识改回"底层"。


## 十一、坏道隔离与规避

### 11.1 坏道隔离

- 每个子文件夹日志区按独立extent分配，之间预留至少1簇隔离带。
- 物理距离尽量远。
- 恢复时按物理区域分片扫描。

### 11.2 坏道规避与固件协同

- **写入触发修复**：存储抽象层检测到读错误时，主动发起一次写入，触发固件重映射。
- **分区级坏道位图**：元数据引擎维护坏道位图，分配器跳过这些区域。
- **S.M.A.R.T.健康监控**：存储抽象层定期采集关键参数，恶化超阈值时触发数据迁移。
- **写入即修复策略**：对标记为"待处理"的扇区执行写入时，触发固件重映射。


## 十二、EFI驱动与引导兼容

### 12.1 EFI驱动定位

- 直接做EFI驱动，一个程序，一次解决。
- 不整合EFI系统分区，分区工具独立划分。
- 兼容区32-64MB，只承担传统BIOS引导和引导配置。

### 12.2 EFI驱动核心

- 实现 `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL` 协议。
- 提供 `OpenVolume()`、`Open()`、`Read()` 等函数。
- 将UEFI文件操作请求映射到文件系统磁盘格式。
- 复用兼容层逻辑：主总账 → 引导文件表 → 内核文件。

### 12.3 开发环境

- **框架**：EDK II (TianoCore)。
- **参考**：FvSimpleFileSystemDxe（EDK II自带只读示例）。
- **调试**：QEMU + OVMF。
- **许可证**：BSD兼容。

### 12.4 引导流程

```
阶段一：UEFI固件
  └── 加载EFI驱动
  └── 读主总账 → 读引导文件表 → 读内核文件
  └── 加载内核到内存，跳转执行

阶段二：内核初始化
  └── EFI驱动保留为只读转发层

阶段三：系统启动完成
  └── 用户态高级驱动加载
  └── 所有文件操作走高级驱动
```


## 十三、兼容层（绝不蓝屏）

### 13.1 绝对安全路径

- **零动态内存分配**：所有缓冲区编译期确定大小。
- **零阻塞**：所有I/O带硬性超时（100ms）。
- **零递归**：迭代 + 固定深度上限（16层）。
- **零断言**：所有情况有错误返回路径。
- **零复杂状态机**：每次调用独立，状态存在调用方。

### 13.2 操作集

| 操作 | 实现 | 崩溃可能性 |
| :--- | :--- | :--- |
| 读扇区 | 带超时 | 无 |
| 写扇区 | 带超时 | 无 |
| 校验和验证 | CRC32C硬件指令 | 无 |
| 主总账解析 | 固定偏移+结构体+校验和 | 无 |
| 引导文件表解析 | 固定偏移+固定结构体 | 无 |
| 内核文件读取 | 顺序读+固定缓冲区 | 无 |

### 13.3 代码量估算

| 模块 | 代码量 |
| :--- | :--- |
| 主总账读取+校验 | ~200行 |
| 引导文件表解析 | ~100行 |
| 扇区读写（带超时） | ~300行 |
| 内核文件读取 | ~200行 |
| 错误处理 | ~200行 |
| 平台包装层 | ~300行 |
| **合计** | **~1300行** |


## 十四、元数据引擎（v0.6.1 新增）

> **本节为 v0.6.1 新设**。原稿中元数据引擎的职责只出现在 §1.1 的模块表里，
> 没有独立章节承载其机制。而它是本文件系统唯一维护**权威状态**的组件——
> 总账、事务、写时复制、快照、子卷都由它定义。缺少它的正式描述，
> 格式实现与恢复逻辑都失去依据，故补入本节。
>
> 实现载体：开发包 [`40-元数据引擎`](NXFS开发包/40-元数据引擎/开发包.md)。

### 14.1 定位与职责

| 项 | 内容 |
| :--- | :--- |
| 运行位置 | 用户态进程（与 §1.1 一致） |
| 许可证 | 可闭源 |
| 权威性 | **维护文件系统的权威状态**；其他模块（翻译层缓存、存储层）只能持有它的**派生视图** |

| 职责 | 说明 |
| :--- | :--- |
| 总账 | 权威状态源：主总账（分区头）、副总账（分区中部），结构相同 |
| 事务 | 启动 / 提交 / 回滚；四种范围（单文件 / 多文件 / 元数据 / 结构变更） |
| 写时复制 | 未提交修改对其他读者不可见；提交是唯一可见性边界 |
| 快照 | 只读与可写快照；快照树（父子关系） |
| 子卷 | 独立命名空间；克隆（全量 / 写时复制） |
| 责任主体 | 元数据变更后回传受影响主体集合，供翻译层精确裁剪缓存 |
| 日志量核算 | **判定**是否需强制检查点（**执行**在 §九 的检查点策略） |

### 14.2 总账作为权威状态源

字段构成见 §2.3。实现约束如下：

| 约束 | 理由 |
| :--- | :--- |
| 字段偏移与大小**一经冻结不可改** | 必须能在安全路径（§十三）中**零分配、固定偏移**地解析 |
| 引导文件表**固定 4 条** | 与 §2.3 一致；解析不得依赖扫描 |
| **降级可见性口径必须一致**（v0.6.2 补充） | 主份不可用这件事，在"总账视图"与"挂载状态"两个观察面上**必须同时置位**：视图回答"**这份账**的主份能不能信"，状态回答"**这次挂载**是否发生过主份不可用"。不变量：数据取自副份 ⇒ 两个观察面都表明主份不可用。首次合练（20+30+40）的观察项 O-1 正是这条被违反的实例——两处口径不一致会让按视图判断的调用方得出相反结论 |
| 副总账是**独立第二份权威副本**，不是镜像备份 | 恢复时以校验和通过的那份为准，见 §9.1 降级链 |
| 可引导卷上引导文件表所指文件**豁免物理迁移** | 否则冷启动阶段一按总账 LBA 直读会读到已蒸发或复用的块 → 引导失败 |

### 14.3 事务与可见性

**唯一可见性边界是事务提交**：

- 提交前：旧版本可读，新版本完全不可见；
- 提交后：新版本可读；
- **不存在"半新半旧"的可读状态**——这是写时复制的全部意义。

提交必须同时返回两个信息，缺一不可：

| 返回项 | 作用 | 只给它的后果 |
| :--- | :--- | :--- |
| 提交序号 | 全局基准点，用于判断"整体视图是否过时到需要重整" | 只有它 → 失效风暴 |
| 受影响主体集合 | 精确裁剪范围 | 只有它 → 无法判断陈旧性 |

**四种事务范围的语义差异必须在接口上可见**（§1.2 的 C ABI 已表达）：

| 范围 | 含义 | 代价 |
| :--- | :--- | :--- |
| 单文件 | 单文件内原子 | 最低 |
| 多文件 | 跨文件原子，**可能进入跨文件区（§四）** | 高（需后台分发） |
| 元数据 | 元数据 + 数据一致（默认） | 中 |
| 结构变更 | 目录重命名等结构操作原子 | 中 |

### 14.4 三种失败必须区分

这是元数据引擎**最容易实现错**的地方。提交路径可能产生三类结果：

| 结果类别 | 正确处置 | 错误处置的后果 |
| :--- | :--- | :--- |
| 数据未写入 | **可重试** | — |
| 数据可能写了一半 | 靠 CRC32C 识别并丢弃 | 若当"未写入"重试，会叠加两次半写 |
| **数据已写入、完整性不确定** | **不可重试**（重试会制造第二次不确定），必须靠 CRC32C 事后核验 + 降级链 | 若重试，从"一个不确定"变成"两个不确定" |

第三类正是 §9.1"主总账校验和不过 → 走副总账"这条路径的**具体成因**，
因此必须独立成码，**不可与通用 I/O 错误合并**。

### 14.5 快照与子卷

| 项 | 说明 |
| :--- | :--- |
| 快照创建 | 写时复制，**不复制数据**；创建时只冻结元数据视图 |
| 只读 / 可写 | 差别仅在写入时的写时复制目标；对外由 `writable` 标志表达 |
| 快照树 | `parent` 构建父子关系，便于批量销毁与空间核算 |
| 子卷克隆 | **全量**（配合 §8.1"迁入时天然紧凑"）与 **写时复制**（共享 extent） |

> ⚠️ **快照不等于备份**。快照与源数据位于**同一卷**，卷级损坏会一并丢失。
> 对外描述不得称其为备份。

### 14.6 与相邻章节的边界

明确划分，避免实现时职责互相渗漏：

| 内容 | 归属 |
| :--- | :--- |
| 总账结构、事务语义、写时复制、快照、子卷 | **本节** |
| 日志区物理布局、检查点执行、升降层执行、恢复重放 | §三、§九、§十 |
| 检查点**判定**（日志量核算） | **本节**（执行在 §九） |
| 责任主体的定义与世代号语义 | 本节定义；缓存消费方为 §6.4 的翻译层 |
| 块内预留与增长 | §五 |
| **副本地址与布局推导规则**（副总账 LBA、副引导表 LBA） | §2.3 定义规则与唯一实现点；**本节只使用地址值，不自建公式** |

**本节对布局规则的引用纪律**（实现侧已实测到重复，故写明）：

- 元数据引擎需要"另一份副本的地址"来做双副本比对与修复，这个地址**由兼容层上报**
  （盘上自描述字段），或取自 §2.3 的唯一实现点；
- **不得**在本节重写容量推导公式。实现仓 `40-元数据引擎/ledger.c` 现有一处这样的重写
  （`led_secondary_lba()`，注释自陈"与包 20 一字不差"），它正是本条纪律要消除的对象；
- 该重写**不只是"难看"**：一旦两侧漂移，40 会拿着自己算出的 LBA 去读写一个**不同的扇区**，
  而全链路没有任何一处会报错——这是静默的数据面风险，不是代码风格问题。

## 十五、NAND可选缓存（新增）

> ⏸️ **本整节属于「二期」，已整体冻结：暂不实现，一个都不做。**
>
> 开启条件：**一期（机械盘侧）开发完成并进入可用阶段后**再开启——
> 这是状态条件，不是日历时间点。
>
> **冻结的工程理由**（不只是排期）：
> 1. NAND 是**纯增量功能**，核心文件系统不依赖它（§15.5 明确"核心专利不依赖 NAND 缓存"）；
> 2. 它的收益是**性能，不是正确性**——在正确性还没跑通时做性能优化，会把调试面翻倍：
>    出现数据不一致时无法判断是 CoW/日志错了还是缓存层错了；
> 3. 它会**污染多个模块的边界**：§1.1 把"NAND 缓存管理"写在存储抽象层职责里，
>    若现在实现，存储层会同时承担"介质访问"与"缓存策略"，而后者需要块分配与
>    翻译层的能力，形成循环依赖。
>
> **当前只做了接口预留**（见下），**没有任何实现**：
>
> | 位置 | 预留内容 | 当前行为 |
> | :--- | :--- | :--- |
> | 存储抽象层 | NAND 能力探测点 | **恒返回"不可用"** |
> | API 规范 | `NXFS_CAP_NAND_CACHE` / `NXFS_VOLATTR_HAS_NAND_CACHE` / `NXFS_FEATURE_NAND_CACHE` | 能力位预留，**均不置位、不可请求** |
>
> **纪律**：请求 `NXFS_FEATURE_NAND_CACHE` 时按"未知位必须被忽略"处理并在
> `features_ignored` 中回报，**不返回错误、不静默置位**；核心任何路径中不得出现
> "NAND 可用则…"的分支。
>
> **解冻前置条件**：① 元数据引擎/日志/块分配/翻译层的验收标准全部通过；
> ② 有稳定的性能基准框架；③ 跨文件区的权威不对称规则已稳定；
> ④ 世代号缓存机制已证明无陈旧读；⑤ 完成 FTO 检索。
>
> ⚠️ **解冻时必须先裁定一个设计问题**：§15.3 的读取路径是"先查 NAND 缓存文件，
> 没有则查机械盘"，这意味着 NAND 条目**先于**机械盘日志生效。它与跨文件区的
> "目标侧权威、源侧仅作辅证"规则需要对齐——NAND 条目在迁移完成前属于哪一侧？
> 不先裁定这一点，解冻后会直接与缓存一致性机制冲突。
>
> 以下为原稿内容，**存档保留**以备解冻时参照。

### 14.1 设计原则

- **NAND是缓存，不是权威数据源**。NAND死了，机械盘上的数据必须完好。
- **完全依赖高级驱动**：高级驱动在NAND上创建一个**特殊文件**作为缓存容器，所有缓存逻辑在用户态完成。
- **专利规避**：通过用户态实现，改变技术实施主体和场景，避免触碰设备级和文件系统级NAND缓存专利。

### 14.2 架构定位

```
┌─────────────────────────────────────────────┐
│ 高级驱动（用户态）                            │
│ 元数据引擎、事务、日志                       │
└─────────────────────────────────────────────┘
                    ↕
┌─────────────────────────────────────────────┐
│ 存储抽象层                                    │
│ 判断：NAND可用？ → 写入NAND缓存文件          │
│        NAND不可用？ → 直接写入机械盘日志区    │
└─────────────────────────────────────────────┘
                    ↕
        ┌───────────┴───────────┐
        ↓                       ↓
┌───────────────┐     ┌───────────────┐
│ NAND缓存文件   │     │ 机械盘         │
│ （特殊文件）   │     │ 日志区+数据区  │
│ 快速写入       │     │ 权威数据源     │
│ 断电可能丢失   │     │ 断电安全       │
└───────────────┘     └───────────────┘
```

### 14.3 工作流

**写入路径（NAND可用时）：**

1. 数据写入NAND上的特殊缓存文件（顺序写，NAND速度）。
2. 缓存文件的元数据同步写入机械盘日志区（记录“数据X在NAND文件偏移Y”）。
3. 向用户报告“写入成功”。
4. 后台空闲时，从NAND迁移到机械盘最终位置。
5. 迁移完成后，机械盘日志更新，NAND缓存空间回收。

**写入路径（NAND不可用时）：**

- 走原有路径：数据写入机械盘日志区，后台迁移到最终位置。

**读取路径：**

- 先查NAND缓存文件是否有该数据 → 有则直接返回。
- 没有则查机械盘。

### 14.4 故障场景处理

| 场景 | 后果 | 恢复方式 |
| :--- | :--- | :--- |
| NAND写入中断电 | NAND数据丢失，但机械盘日志已记录 | 挂载时读机械盘日志，发现NAND条目无效，回滚该事务 |
| NAND迁移中断电 | NAND数据可能已部分写入机械盘 | 机械盘日志有迁移记录，按日志决定完成或回滚 |
| NAND盘彻底死亡 | 缓存数据全部丢失 | 机械盘日志中标记“NAND缓存”的条目全部失效，回滚对应事务 |
| NAND盘移除 | 同“彻底死亡” | 挂载时检测NAND不存在，自动降级为纯机械盘模式 |

### 14.5 专利规避设计

- **用户态实现**：缓存逻辑完全在用户态高级驱动中，不涉及内核文件系统或硬盘固件。
- **特殊文件容器**：在NAND上创建一个固定大小的稀疏文件，内部实现日志/缓存结构。避免“设备控制器”、“集成于HDD内部的NAND”等硬件特征。
- **日志结构、文件系统元数据感知**：采用独特的数据管理策略，降低“等同原则”风险。
- **作为可选功能发布**：不绑定核心文件系统。核心专利不依赖NAND缓存。

### 14.6 性能收益

| 操作 | 纯机械盘 | 加NAND缓存 |
| :--- | :--- | :--- |
| 4K随机写入 | 800-1500 IOPS | **50000+ IOPS** |
| 写入延迟 | 5-15ms | **0.1-1ms** |
| 后台迁移 | 无 | 不影响前台写入 |
| 断电恢复 | 1-3分钟 | 1-3分钟（机械盘日志不变） |
