## 边界（先看这段）

**需要读**：`10-公共约定.md`（`INV-1`~`INV-3`、`INV-6`、`INV-7`）；`20` 的六个安全路径操作。

**不需要读**：CoW、事务、跨文件区、块分配、翻译层缓存。**引导路径零恢复依赖**
（见 `20` 包），因此这些模块在阶段一完全不参与。

**本包不做**：不做写入、不做恢复重放、不做检查点、不做分配。
任何一个"顺手也做了吧"的想法都会破坏"绝不蓝屏"的前提。

---

## 定位（设计稿 §12.1）

- **直接做 EFI 驱动，一个程序，一次解决。**
- **不整合 EFI 系统分区** —— 分区工具独立划分。
- **兼容区 32–64 MB**，只承担传统 BIOS 引导和引导配置。

## 关键设计点

### 1. 实现 `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL`

| 协议函数 | 映射到 |
| :--- | :--- |
| `OpenVolume()` | `ledger_parse` → 得到根日志区偏移 |
| `Open()` | 只读路径解析（深度 ≤ `NXFS_SAFEPATH_MAX_DEPTH`） |
| `Read()` | `kernel_read` / `sector_read` |
| `Close()` | 释放句柄 |
| `GetInfo()` | 从总账读容量信息 |

**复用链**（`§12.2`）：主总账 → 引导文件表 → 内核文件。
这条链**只用到 `20` 包**，不涉及其他任何模块。

### 2. 开发环境（`§12.3`）

| 项 | 值 |
| :--- | :--- |
| 框架 | **EDK II (TianoCore)** |
| 参考 | **`FvSimpleFileSystemDxe`**（EDK II 自带的只读示例） |
| 调试 | **QEMU + OVMF** |
| 许可证 | BSD 兼容 |

**建议的起步方式**：直接以 `FvSimpleFileSystemDxe` 为骨架改造，替换其读取后端为
`20` 包的安全路径。这比分头写一个协议实现快得多，且天然符合 UEFI 的调用约定。

### 3. 三阶段引导流程（`§12.4`）

> 注：此处"阶段"是 UEFI 引导的既有术语，与开发进度无关。

```
阶段一：UEFI 固件
  └── 加载 EFI 驱动
  └── 读主总账 → 读引导文件表 → 读内核文件
  └── 加载内核到内存，跳转执行

阶段二：内核初始化
  └── EFI 驱动保留为只读转发层

阶段三：系统启动完成
  └── 用户态高级驱动加载
  └── 所有文件操作走高级驱动
```

**阶段转移是所有权交接，必须显式化**（否则存在两个都自认权威的窗口）：

```c
nxfs_status_t boot_handover(nxfs_handle_t volume,
                            const nxfs_boot_handover_options_t *opts,
                            nxfs_boot_handover_result_t *out);
```

| 要求 | 说明 |
| :--- | :--- |
| **只允许推进，不允许回退** | `target` 必须 ≥ 当前阶段 |
| **交接时递增卷级世代** | `volume_gen`，使所有缓存整体失效一次 |
| **EFI 侧元数据缓存整体作废** | 阶段二只允许**无缓存直读** |

**为什么阶段二必须无缓存直读**：若 EFI 转发层带自己的元数据缓存，而阶段三高级驱动
已改写元数据，就会出现"EFI 返回陈旧元数据"的情形——这是热路径返回陈旧数据的翻版。
代价是阶段二每次读都要过总账/日志，但阶段二本身是短暂时段，值得。

### 4. 引导路径必须零恢复依赖（`§12.4` 的硬约束）

阶段一只有：**主总账 → 引导文件表 → 内核文件**。

**绝不能依赖用户态恢复流程**（重放、检查点、跨文件区分发都需要用户态）。因此：

| 要求 | 说明 |
| :--- | :--- |
| 总账校验和验证 + 副总账降级 | 必须能在**纯固件环境、无分配器、无日志重放**下完成 |
| 固定偏移 + 固定结构体 | 不得要求扫描或重建索引 |
| `from_secondary` 字段 | 显式表达"已降级到副总账"，使固件侧也能如实上报 |

### 5. `INV-6`：内核文件豁免物理迁移（与 `70` 的交汇点）

**可引导卷上，引导文件表所指文件豁免物理迁移。**

**若不遵守会怎样**：设计稿 §6.2 允许大文件独立成块，§8.2 允许块级整理
"更新父日志偏移"。若内核文件被迁移，则下次冷启动时阶段一按**总账记载的 LBA 直读**
会读到**已蒸发或已复用的块** —— 结果是**引导失败**，而这正是"绝不蓝屏"要防的事。

因此：

- `defrag` 的 `allow_kernel_file_move` 在可引导卷上**被强制为 0**；
- 实现上更稳的做法是让内核文件**一开始就分配到长期稳定的连续区域**
  （见 `90` 包的 `AC-90.12`），而不是"先分配再指望不迁移"。

### 6. `INV-7`：可引导能力 ≠ 卷可引导

| 概念 | 字段 | 含义 |
| :--- | :--- | :--- |
| 实现具备引导能力 | `NXFS_CAP_BOOT` | 这个 EFI 驱动二进制存在且可用 |
| **此卷可引导** | `NXFS_VOLATTR_BOOTABLE` | 挂载时**探测**得出（引导文件表是否有效） |

**混淆二者是最常见的兼容性事故来源**：同一块盘换台机器就会行为不一致。
`nxfs_boot_stage_t` 的第四个值 `NOT_BOOT_VOLUME = 255` 让"数据盘"成为**显式状态**，
而不是"引导相关调用会失败"这种隐式约定。

### 7. 代码量基线（`§13.3`）

| 模块 | 估算 |
| :--- | ---: |
| 主总账读取 + 校验 | ~200 行 |
| 引导文件表解析 | ~100 行 |
| 扇区读写（带超时） | ~300 行 |
| 内核文件读取 | ~200 行 |
| 错误处理 | ~200 行 |
| 平台包装层 | ~300 行 |
| **合计** | **~1300 行** |

> 这 1300 行**就是 `20` 包**。EFI 驱动本身是在此之上的一层协议适配，
> 因此本包的实际新增代码量应远小于 1300 行——**如果明显超出，说明职责没划清**。

## 常见坑

1. **不要在 EFI 驱动里加功能** —— 每加一个"顺手"的功能都在削弱"绝不蓝屏"。
2. **不要给阶段二加缓存** —— 会与阶段三的高级驱动产生陈旧读。
3. **交接必须显式且单向**，不要靠"驱动加载了就算接管"。
4. **`NXFS_CAP_BOOT` ≠ `VOLATTR_BOOTABLE`**。
5. **内核文件不迁移**（`INV-6`），且要在分配阶段就保证连续性。
6. **不要整合 EFI 系统分区**（`§12.1`）—— 分区工具独立划分。
7. **QEMU + OVMF 是必须的验证环境**，不要只在真实机器上试（会变砖风险高且难调试）。
8. **`FvSimpleFileSystemDxe` 是骨架参考**，不是可直接发布的代码——注意其许可证与
   本包的 BSD 兼容要求的差异。

### 已由 L2-pre 实测钉住的三条（**先读，能省一整轮调试**）

> 来源：`nxfs-impl/tools/vm/` + `verify/vm_smoke.py`（真 OVMF × 真 `EFI_BLOCK_IO` × 真镜像，
> **15 项 / 0 失败**）。它们不是推测，是**已经在固件里踩过**的事实；简报
> `NXFS开发包/交接报告/B0-EFI只读驱动.md` 只做导航，条文以本节为准。

9. **不要自抄 UEFI 结构体，用 `20` 的 `safepath_uefi_types.h`**。该文件的
   `nxfs_efi_block_io_media_t::last_block` 曾被写成 `uint32_t`（偏移 20），而规范的
   `EFI_BLOCK_IO_MEDIA.LastBlock` 是 `EFI_LBA`＝**`uint64_t`**（偏移 **24**）⇒ 真固件里
   容量恒读成 `(0+1)*sectors_per_block` ⇒ `kernel_read` 的范围检查判 `NXFS_ERR_INVALID_ARG`
   ⇒ **固件读不到内核文件**。
   **为什么它极难自查**：当时的静态断言 `offsetof(last_block) == 20` 与假 media **同源**
   ⇒ 自洽但错误（"断言没有牙"），**只在真固件下才现形**。
   **判定手段（请照用）**：把固件给的**同一个 `media` 指针**按规范布局**再解释一遍**，
   两个读数对照——128 MiB 镜像得 **262144** 块（规范）vs **1** 块（旧定义）。
   现在 `20` 已修，并新增**金标准字节镜像**用例（字节序列与结构体成员序无关 ⇒ 能证伪结构体）。
10. **`__chkstk` / `_fltused` 这两个链接符号**：`20` 的 UEFI 包装里有 4 KB 栈缓冲
    （`uint8_t blk[4096]`）⇒ x64 ABI 下栈帧 > 4 KB 会引用 `__chkstk`；UEFI 目标链接还需
    `_fltused`。**`20` 的阶段 4 只编译不链接，所以它自己的验收看不见这两条** ⇒ `B0` 必须
    **真链接一次**（EDK II 链接 `BaseLib` 即可；若需改 `20` 的缓冲为静态，走统筹代改流程）。
11. **判据形态**：标记式（`NXFS-VM-PROBE OK` / `FAIL <原因>`），**QEMU 退出码不参与判定**
    （固件自己会退出，退出码不可靠）；并且**负对照必须有牙**——本包的对应项是
    `AC-B0.3`：篡改主总账一字节 ⇒ 必须看到 `from_secondary == 1` **且降级后链路仍通**。

## 交付物
