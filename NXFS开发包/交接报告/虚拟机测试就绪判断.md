# 就绪判断 · 正式虚拟机测试（而非合跑）

> **问题**：现在能不能从"合跑"（`verify/joint/` 同二进制 + 内存夹具）升级到**正式虚拟机测试**？
> **结论**：**暂不具备**——缺 3 项硬前置（其中 2 项可立刻补，1 项属环节3）。但**存在一个更早、更便宜、可立即执行的中间台阶（L1）**，
> 它是 VM 测试的**直接前置**，也是当前最该做的一步。
>
> 判断依据：实现仓现状（`git`）、`NXFS开发包/`（各包 AC 与环节表）、
> 设计稿 **§12.3**（"调试：QEMU + OVMF"、"框架：EDK II"）与 **§12.4**（三阶段引导）。
> **一切以仓库现状为准**；本文只做判断与前置清单，不含"我已实现"的声明。

---

## 1. 分级：现在能到哪一级

| 级别 | 内容 | 现在可做？ | 缺口 |
| :--- | :--- | :---: | :--- |
| **L0 合跑（现状）** | `verify/joint/` 把 20/30/40/50 链进**一个二进制**，在**内存夹具镜像**上跑 `J1~J8`（**248 项 / 0 失败**，已进 CI） | ✅ **已上线** | —— |
| **L1 宿主侧真实镜像端到端** | **真实镜像文件** + 20 的**用户态文件设备** + 30/40/50 真栈（`format` → 只读 `mount` → 读总账/表 → 定位日志树） | ⚠️ **可做，但缺一个宿主工具** | 无 CLI/工具目录；需接线（**不需要 B0/A0**） |
| **L2 UEFI 虚拟机（QEMU + OVMF）跑只读驱动** | 设计稿 §12.3/§12.4 **阶段一**：固件加载 EFI 驱动 → 读主总账 → 读引导文件表 → 读内核文件 | ❌ **不具备** | ① `B0` 未开工；② **无分区表写入** + 无镜像工具；③ 本机无 QEMU/OVMF |
| **L3 Windows 实机/VM 挂载** | 设计稿 §十三 + `A0` 用户态驱动 | ❌ **不具备**（环节3） | `A0` 未开工；且**按设计 OS 不应自动挂载**（MBR `0x7F` / 随机 GUID 的选择就是为了避免被 Windows/Linux 误认） |

## 2. 为什么 L2 现在不行（逐条带证据）

| 缺口 | 证据（当前事实） |
| :--- | :--- |
| **① 客户机侧驱动不存在** | 实现仓只有 `20`/`30`/`40`/`50` 四个目录；环节表把 `B0`（EFI 只读驱动）与 `A0`（Windows 集成层）排在**环节3**。没有驱动，"虚拟机里挂载"就无从发生 |
| **② 没有任何代码写分区表** | `NXFS_MBR_TYPE_BYTE` / `NXFS_GPT_TYPE_GUID` 目前只出现在：API 常量（`nxfs.h`）、API 文档、一致性自检，以及**总账里的 `fs_type_guid` 字段**（夹具写入）。**MBR/GPT 分区表本身无人写** ⇒ OVMF 看不到可识别的分区 |
| **③ 没有镜像工具 / CLI** | 实现仓无 `tools/` 或 CLI 目标；现有镜像都是**测试内**构造（夹具 `nxfs_fx_build_minimal()`）或 40 测试内格式化 |
| **④ 本机工具链缺失** | `qemu-system-x86_64` / `qemu-img` / OVMF **均未找到**（`wsl.exe` 在，但未装 QEMU） |
| **⑤ 写入路径才到首步** | 环节2 刚开始：`50` 只做到"环节2 首步"（`AC-50.1~3` + `9`），`60`/`70` 未开工。**但这一条对 L2 不是阻塞**（见下） |

## 3. 好消息：三件"看似缺"的其实已具备

1. **20 已有 UEFI 平台包装且已交叉验证**：`safepath_platform_uefi.c`，六阶段里含 **freestanding 编译**与**对侧平台（`x86_64-uefi`）交叉链接**——`B0` 的地基在。
2. **"真实 OS 文件即设备"已实现**：`nxfs_sp_user_open(path_utf8, …)`（普通文件/卷设备，带 `read_only` 标志与硬性超时语义；Windows 侧 `FILE_FLAG_OVERLAPPED`），并已有 **18 项真实文件端到端测试**。⇒ **L1 的工具只需接线，不必新造设备**。
3. **格式化入口已存在**：`nxfs_meta_ledger_format(ctx, req, …)`（40）。⇒ L1/L2 的镜像可以用**自家代码**格式化，而不是手工拼字节。

> **补充（对 L2 的减负）**：§12.4 **阶段一只走 20 的安全路径**（总账 → 引导文件表 → 内核文件），
> **不需要** 70/90 的目录项语义、也不需要 60/写入路径。所以 "B0 + 镜像工具 + 工具链" 就能跑通
> L2 的第一条验收，**不必等环节2 做完**。

## 4. 最小前置清单（按建议顺序）

| # | 前置 | 归属 | 规模 |
| :-: | :--- | :--- | :--- |
| 1 | **宿主镜像工具**（L1 载体）：`format`（20 user 设备 + 30 + 40 `format`）→ 校验 → 只读 `mount` → 打印总账/表/日志树定位结果；可选 `--verify` 复跑一致性 | 建议**开新流**（长期维护的工具）；规范已够用，无需新裁定 | 小～中 |
| 2 | **分区表写入的归属与形态**：工具只写"从某偏移开始的 NXFS 卷"（分区表交给 `sgdisk`/`diskpart`），还是**生成整盘镜像**（含 MBR/GPT） | **规范层裁定（统筹）** | 小（一条裁定 + 一处文档） |
| 3 | **`B0` 最小只读驱动**：`EFI_SIMPLE_FILE_SYSTEM_PROTOCOL`（参考 EDK II 的 `FvSimpleFileSystemDxe`），先做"能列出并读出内核文件" | 环节3，**开新流**（开发包已就绪） | 中～大 |
| 4 | **QEMU + OVMF** 工具链（Windows 原生或 WSL 内；OVMF 用发行版固件包） | 环境准备（非代码） | 小 |
| 5 | **L2 冒烟脚本**：生成整盘镜像 → `qemu-system-x86_64 -bios OVMF … -drive file=image` → 跑 EFI 驱动 → 断言"列出/读出内核文件" | 与 3 同流 | 小 |

## 5. 建议路径（省时间）

```
L0（已上线）→  L1 宿主真实镜像端到端  →  同时开 B0 流  →  分区表裁定  →  L2 QEMU+OVMF 冒烟  →  L3（A0，环节3）
                  ↑ 现在就能做            ↑ 与 L1 并行            ↑ 一条裁定      ↑ 工具链装好即可
```

**为什么不先做 L2**：L2 的三项缺口中，`B0` 是量最大的一项；而 L1 能**先把"真实镜像"这条链验穿**
（format/mount/定位在**真文件**上成立，而不是内存夹具），把 L2 变成"只差驱动与固件"的问题。
L1 一旦绿，L2 的风险面就只剩 `B0` 本身与固件行为。

---

## 6. 需要裁定的三点（我这边可立即定）

1. **分区表归属与形态**：建议 **工具支持两种模式**——`--volume-only`（给定偏移，供 `sgdisk`/`diskpart` 独立划分，符合设计稿 §12.1"分区工具独立划分"）与 `--whole-disk`（生成含 MBR `0x7F` / GPT 随机 GUID 的整盘镜像，供 VM 直接挂）。**默认 `--volume-only`**，`--whole-disk` 供 VM/验收使用。
2. **L1 的载体**：建议**开新流**（工具要长期演进、要加子命令），而不是统筹代做；若希望我先把骨架与 `format` 路径接线跑通，也可以由我起第一版再交出去。
3. **L2 的验收面**：建议**先钉"驱动挂载成功 + 能列出并读出内核文件"**（阶段一的前半），**跳内核执行留给后续**——因为"跳内核"需要真的有一个内核镜像与内存布局约定，那属另一条线。
