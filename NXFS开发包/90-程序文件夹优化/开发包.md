## 关键设计点

### 1. 程序标记放在父日志条目里（不是文件属性）

`§6.1` 的关键设计：标记存在**父日志条目的"类型标记"字段**（1 字节，见 `50` 包）。

**为什么这样设计**：翻译层在读取子文件夹偏移时，**同一簇内顺手**就能拿到类型标记，
不需要额外一次读。这是"程序启动近原生延迟"的基础设施之一。

**实现要求**：

- 该字段只有 1 字节，取值必须节流：**普通 / 程序** 两个值即可，
  不要往里塞多种标志（需要扩展时用父日志条目的 `状态` 字段的剩余取值，
  或另加字段——但要注意 `50` 包的条目宽度约束）。
- 类型标记是 `PARENT_LOG_ENTRY` 责任主体的内容 → 变更时**递增该主体世代**，
  不是递增文件夹主体。这保证只有该条目的缓存失效。

### 2. 传播是**继承 + 可覆盖**，不是复制

- 程序文件夹下的子文件夹**默认继承**；
- **可显式覆盖**。

**实现纪律**：不要在下创建时把标记**复制**到子项——那样覆盖父项后，
已存在的子项不会跟着变，产生不一致。正确做法是：

```
有效值(child) = child.explicit_flag ?? 向上找最近的显式标记
```

即**求值在读取时沿链向上解析**，标记只存**显式设置**的那一层。

代价是读取时的链式查找（通常只 1–2 跳，因为实践中很少深嵌套），
换来的是"改父项立即对所有未显式覆盖的子项生效"。

**API 已为这个语义留好位置**：

```c
/* dir_create 用两个参数区分"未指定"与"显式设为 false" —— 三态，不是二态 */
nxfs_status_t dir_create(..., uint32_t program_folder_set, uint32_t program_folder, ...);
```

`program_folder_set == 0` 表示继承；`== 1` 时 `program_folder` 才是显式值。

> ⚠️ `nxfs.h` 当前的 `dir_create` 已含这两个参数，但**未定义对应的 `NXFS_*` 常量名**。
> 实现前应先在 API 仓库补上（或在包内暂用 `0/1` 并在注释中说明）。

### 3. 程序块内部分区（`§6.2`）

```
[日志区][程序文件区（只读为主）][写区（日志/存档/配置）][日志区]
```

| 分区 | 内容 | 管理规则 |
| :--- | :--- | :--- |
| **程序文件区** | exe、DLL、资源 | **紧凑排列**（只读为主，不需要预留增长空间） |
| **写区** | 游戏运行时的日志、存档、配置 | 按**普通块规则**管理（即 `70` 的预留 + 间隔规则） |

**关键洞察**：程序文件区**不需要预留**（它们很少增长），写区**需要预留**。
把两者混在一个预留策略下会浪费大量空间。

**实现要求**：块内分区是**布局约定**，不是两个独立块。块的日志区仍在两端（`70` 的规则）。

### 4. 大文件独立成块（`§6.2`）

- 阈值：**> 64 MB**。
- 独立成块 + **连续区域**，目标是**一次寻道读完**。

**与 `70` 的 `INV-6` 的交汇点**：内核文件通常是大文件，且**可引导卷上豁免迁移**。
因此"大文件独立成块"与"内核文件豁免迁移"要一起考虑：
内核文件应当**一开始**就分配到长期稳定的连续区域，而不是先分配再指望不迁移。

### 5. 文件类型识别三层（`§6.5`）

| 层级 | 规则 | 处理 |
| :--- | :--- | :--- |
| 第一层 | 扩展名 + 文件头**一致** | 按对应类型处理 |
| 第二层 | 扩展名与文件头**不一致** | **按文件头处理**（文件头更可信） |
| 第三层 | 无法识别 | 按普通文件处理 |
| 用户显式标记 | 覆盖自动识别 | 指定程序目录 |

**纯函数，可以先做**：三层识别是一组无状态规则（读扩展名 + 读文件头若干字节），
不依赖 CoW/事务/日志。**一期就能实现**。

**实现纪律**：

- 第二层"按文件头处理"是**故意**的：扩展名可以骗人，文件头不容易。
  但要注意**不要**因此把 `.txt` 改名成 `.exe` 就当真程序——识别的是"文件头声明的类型"，
  用于**放置与读路径决策**，不是安全判定。
- 第三层必须**安全兜底**：无法识别 → 普通文件（不猜测、不报错）。
- 识别结果落在 `nxfs_file_class_t`：`UNKNOWN` / `REGULAR` / `PROGRAM` /
  `HEADER_DECIDED` / `USER_FORCED`。
  注意 `HEADER_DECIDED` 单列一值，是为了让调用方能区分"扩展名和头不一致"这种情形。

### 6. 类型识别结果的缓存

识别结果是"文件元数据"的一部分 → 属于 `FILE` 责任主体。
但**文件夹级**的程序标记属于 `PARENT_LOG_ENTRY`。两者不要混：

| 缓存的事实 | 主体 |
| :--- | :--- |
| 单个文件是否为程序（识别结果） | `FILE` |
| 某文件夹是否为"程序文件夹" | `PARENT_LOG_ENTRY` |

## 常见坑

1. **不要把标记复制到子项** —— 用"读取时沿链解析"，否则父项改动不同步。
2. **`program_folder_set` 是三态**，别把 `false` 和"未指定"混成一个值。
3. **类型标记属于 `PARENT_LOG_ENTRY` 主体**，不是文件夹主体。
4. **程序文件区不需要预留**（只读为主），写区才需要——混用会浪费空间。
5. **第二层按文件头处理**，但这不是安全判定，别拿它当权限依据。
6. **第三层必须安全兜底**（普通文件），不猜测。
7. **识别结果是纯函数，可以先做**，不必等 CoW 与事务。
8. **父日志条目的类型标记只有 1 字节**，不要塞多标志。
9. **内核文件要一开始就分到稳定连续区**，别指望"不迁移"能兜住所有情况。
