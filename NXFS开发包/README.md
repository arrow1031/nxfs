# NXFS 开发包（索引）

> 从[设计稿 v0.6](../新文件系统设计稿.txt) 拆解出的**按块开发包**集合。
> 每个包是自足的：AI 或人只需读**一个包 + 公共约定**即可开工，不必读整份设计稿。

> ⛔ **本目录（meta 仓）只放规范，不放代码。** 实现落在实现仓 `nxfs-impl` 的同编号目录
> （见各包『交付物』段的「落盘位置」）。在 meta 仓里新建 `.c/.h` 是实现错误。

## 怎么用（先读这段，能省最多 Token）

| 你的目标 | 只读这些 | 不要读 |
| :--- | :--- | :--- |
| 动手实现某一块 | `10-公共约定.md` + 该块的 `开发包.md` | 其他任何块、设计稿全文 |
| **接手某个正在进行的动作** | 该动作的 [`交接报告/`](交接报告/) 一份 + `10-公共约定.md` | 其他任何块、设计稿全文 |
| 查全局硬约束（常量/错误码/不变量） | `10-公共约定.md` | — |
| 了解整体架构 | 本文件 + 设计稿 §一、§二 | 各块开发包 |
| 改 API 签名 | `nxfs.h`（在 [nxfs-api-design](https://github.com/arrow1031/nxfs-api-design) 仓库） | — |

> **`交接报告/` 是什么**：① **正在进行**的动作各一份"接下来看什么 / 做什么"（增量与导航，
> 不复述规范原文）；② 新开的动作给一份**开工简报**（自足：边界、器具、门禁、协同规则）。
> 未开工的动作**没有**报告——它们照自己的 `开发包.md` 开工即可。

**为什么这样拆分能省 Token**：每个包的"边界"段明确写出*不需要读什么*。上下文浪费主要来自把无关模块一起塞进对话，而不是输出太长。跨块引用一律用**稳定 ID**（如 `INV-3`、`AC-2.4`、`ERR-70`），因此不必复制原文。

### 环节1 的目标（一期第一个可用里程碑）

按上表依赖顺序推进，**先做到只读可跑**：

```
20 兼容层 → 30 存储层 → 40 元数据引擎（只读）→ 挂载并读出总账与元数据表
```

> **为什么不含"读目录"**：以 `40` 的实际实现为准——`40` 提供元数据表与文件夹日志
> **对象**，但文件夹日志的**载荷语义**（目录项布局）不属它，故 `40` 的 `FREEZE.md`
> 明确声明"目录枚举尚不可用……要等环节2"。读目录需 `50`（日志树定位）
> \+ `70`/`90`（目录项布局），不在环节1 范围内。

## 与 API 规范、实现代码的关系

本目录是**规范层**（每块要满足什么）。对外接口规范与实现代码各在独立仓库：

> - **<https://github.com/arrow1031/nxfs-api-design>** — `nxfs.h` 是 C ABI 单一事实源。
> - **<https://github.com/arrow1031/nxfs-impl>** — 各包的**实现代码**与构建/验收脚本
>   （目录编号与本目录一一对应，如实现仓的 `20-兼容层与安全路径/` 对应本目录的同名包）。

三者分工：

| | API 规范仓库 | 本目录（开发包规范） | 实现仓库 |
| :--- | :--- | :--- | :--- |
| 回答 | *对外暴露什么* | *要满足什么* | *怎么做到* |
| 权威物 | `nxfs.h` | 各块开发包 + 设计稿 | 各包代码 + `build.py` |
| 受众 | 调用方、绑定层 | 实现者、AI 开发会话 | 集成方、CI |
| 形态 | 子模块 `fs-api-design/` | 本仓跟踪 | 子模块 `nxfs-impl/` |

**签名不一致时以 `nxfs.h` 为准**——它是编译期断言验证过的，开发包里的签名只是便于阅读的摘要。
验收标准（`AC-*`）留在本目录：实现仓的测试逐条对应它们，完成情况在本目录该包内标记 `[x]`。
