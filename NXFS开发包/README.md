# NXFS 开发包（索引）

> 从[设计稿 v0.6](../新文件系统设计稿.txt) 拆解出的**按块开发包**集合。
> 每个包是自足的：AI 或人只需读**一个包 + 公共约定**即可开工，不必读整份设计稿。

> ⛔ **本目录（meta 仓）只放规范，不放代码。** 实现落在实现仓 `nxfs-impl` 的同编号目录
> （见各包『交付物』段的「落盘位置」）。在 meta 仓里新建 `.c/.h` 是实现错误。

## 怎么用（先读这段，能省最多 Token）

| 你的目标 | 只读这些 | 不要读 |
| :--- | :--- | :--- |
| 动手实现某一块 | `10-公共约定.md` + 该块的 `开发包.md` | 其他任何块、设计稿全文 |
| 查全局硬约束（常量/错误码/不变量） | `10-公共约定.md` | — |
| 了解整体架构 | 本文件 + 设计稿 §一、§二 | 各块开发包 |
| 改 API 签名 | `nxfs.h`（在 [nxfs-api-design](https://github.com/arrow1031/nxfs-api-design) 仓库） | — |

**为什么这样拆分能省 Token**：每个包的"边界"段明确写出*不需要读什么*。上下文浪费主要来自把无关模块一起塞进对话，而不是输出太长。跨块引用一律用**稳定 ID**（如 `INV-3`、`AC-2.4`、`ERR-70`），因此不必复制原文。

## 总开发期与环节

| 期 | 内容 | 状态 |
| :--- | :--- | :--- |
| **一期** | **机械盘侧全部开发**（`20`～`B0` 共 10 个包） | 🚧 **当前进行中** |
| **二期** | **NAND 相关全部功能**（设计稿 §十五 + 包 `C0`） | ⏸️ **已冻结**，待一期开发完成并进入可用阶段后开启 |

**子开发称"环节"**（不叫"阶段"——"阶段"在本文档另有用途：
B0 的"三阶段引导流程"、`60` 的"四个动作步状态机"）。

| 环节 | 内容 | 包含的包 |
| :--- | :--- | :--- |
| **一期 · 环节1** | **只读最小可跑**：挂载、读总账（含主副降级）、读元数据表 | `20` → `30` → `40`(只读) |
| **一期 · 环节2** | **写入路径**：CoW、事务、日志、分配、回收 | `40`(CoW) → `50` → `70` → `60` |
| **一期 · 环节3** | **集成与优化**：热路径缓存、Windows 挂载、程序文件夹、EFI 驱动 | `80` → `A0` → `90` → `B0` |
| **二期 · 环节1** | **NAND 缓存**（冻结） | `C0` |

> 环节内部及环节之间的先后由**依赖关系**决定（见下表），不另设编号层级。

### 环节1 的目标（一期第一个可用里程碑）

按上表依赖顺序推进，**先做到只读可跑**：

```
20 兼容层 → 30 存储层 → 40 元数据引擎（只读）→ 挂载并读出总账与元数据表
```

> **为什么不含"读目录"**：以 `40` 的实际实现为准——`40` 提供元数据表与文件夹日志
> **对象**，但文件夹日志的**载荷语义**（目录项布局）不属它，故 `40` 的 `FREEZE.md`
> 明确声明"目录枚举尚不可用……要等环节2"。读目录需 `50`（日志树定位）
> \+ `70`/`90`（目录项布局），不在环节1 范围内。

达到这一步即算"基础跑起来"。此后进入**环节2**（写入路径）与**环节3**（集成与优化）。

> **进度**：`20`（兼容层与安全路径）、`30`（存储抽象层）、`40`（元数据引擎）
> **均已实现并冻结**——各包『实现状态』小节列出逐条 AC 与证据，
> 冻结记录见实现仓对应目录的 `FREEZE.md`。
> **环节1（只读最小可跑）达成**：挂载、读总账（含主副降级链）、读元数据表
> （主体 / 快照 / 子卷）已可跑；**目录枚举**要等文件夹日志的载荷语义
> （`70`/`90`），随环节2 推进。
> 下一步是 `50` 日志体系与恢复（环节2 的起点）。

### 二期 · 环节1 的开启条件

**NAND 相关全部已冻结**，待**一期（机械盘侧）开发完成并进入可用阶段**后再开启。
解冻的工程前置条件见 [`C0`](C0-NAND可选缓存/开发包.md)。

## 硬性约束速查（详见 `10-公共约定.md`）

| 约束 | 值 | 说明 |
| :--- | :--- | :--- |
| 安全路径 I/O 超时 | **100 ms** | 硬性，超时即错误返回 |
| 安全路径深度上限 | **16** | 调用/结构深度，**不是**数据分层数 |
| 簇大小 | 4 KB（可 16/64 KB） | |
| 环形槽位 | 4096 B（头 128 + 载荷 3968） | 整页 |
| 分区标识 | MBR `0x7F` / GPT `13073c46-…` | **不要用 `0x8E`**，那是 Linux LVM |
| 索引条目宽度 | 8 B | 4B 簇号 + 2B 长度 + 1B 状态 + 1B 校验 |
| 紧急保留空间 | 5% | 冷数据写入不占用 |
| 检查点间隔 | 30–60 min | 日志超分区 1% 强制 |
| 日志量基线 | 顶层 ~64 KB / 中间 ~3.2 MB / 底层 ~115 MB | 按 1000 文件夹 |

## 与 API 规范、实现代码的关系

本目录是**规范层**（每块要满足什么）。对外接口规范与实现代码各在独立仓库：

> - **<https://github.com/arrow1031/nxfs-api-design>** — `nxfs.h` 是 C ABI 单一事实源。
> - **<https://github.com/arrow1031/nxfs-impl>** — 各包的**实现代码**与构建/验收脚本
>   （目录编号与本目录一一对应，如实现仓的 `20-兼容层与安全路径/` 对应本目录的同名包）。

三者分工：

| | API 规范仓库 | 本目录（开发包规范） | 实现仓库 |
| :--- | :--- | :--- | :--- |
| 回答 | *对外暴露什么* | *要满足什么* | *怎么做到* |
| 权威物 | `nxfs.h` | 各块开发包 + 设计稿 | 各包代码 + `build.py` |
| 受众 | 调用方、绑定层 | 实现者、AI 开发会话 | 集成方、CI |
| 形态 | 子模块 `fs-api-design/` | 本仓跟踪 | 子模块 `nxfs-impl/` |

**签名不一致时以 `nxfs.h` 为准**——它是编译期断言验证过的，开发包里的签名只是便于阅读的摘要。
验收标准（`AC-*`）留在本目录：实现仓的测试逐条对应它们，完成情况在本目录该包内标记 `[x]`。

## 维护规则

1. **改公共约束只改 `10`**，不要在块开发包里重复定义常量——这是 Token 膨胀的主因。
2. 新增验收标准时**沿用所在块的 ID 前缀**（`AC-<块号>.<序>`），保证引用稳定。
3. 实现完成一个验收项，在包内把它标记为 `[x]`，不要删除——保留可追溯性。
4. 设计稿（`新文件系统设计稿.txt`）是**概念层**文档，本目录是**工程层**。二者冲突时：接口以 `nxfs.h` 为准，行为以设计稿为准，若仍冲突则提出来裁定，不要各自解释。
