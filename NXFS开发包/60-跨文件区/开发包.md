## 边界（先看这段）

**需要读**：`10-公共约定.md` §6 移交裁定（三条规则）；`50` 的日志区接口。

**不需要读**：EFI 驱动、程序文件夹优化、Windows 集成。

**本包不做**：不做策略判定（何时分发、分多少）。那是调度层的职责。
本包提供的是**结构 + 状态机 + 恢复规则**。

---

## 职责

跨文件操作（影响多个文件夹的操作）不即时写入目标日志区，而是：

1. 即时写入**跨文件区**并回报用户（低延迟）；
2. 后台空闲时分发到各文件夹日志区；
3. 分发完成后回收跨文件区空间。

跨文件区物理规格：**256 MB – 1 GB**（`10-公共约定` §3）。

## 关键设计点

### 1. 四个动作步的完整状态机（设计稿 §4.1）

| 动作步 | 动作 | 状态标记 |
| :--- | :--- | :--- |
| 操作发生 | 日志写入跨文件区 | **待分发** |
| 后台分发 | 跨文件区 → 文件夹日志区 | **分发中** |
| 分发完成 | 目标日志区确认接收 | **转移完成** |
| 总区回收 | 后台批量清除 | 无 |

**实现要求**：

- 跨文件操作**即时回报用户**（不等分发完成）——这是本机制存在的全部意义。
- **分发操作本身留痕**：哪个文件分发完成就抹除哪个转译条目。**逐条**抹除，不是整批。
- **分发按文件夹聚合**，一次性顺序写入——这是把随机写变顺序写的关键，
  不要逐条下发。

### 2. 恢复逻辑表（设计稿 §4.2，逐行实现，不要简化）

| 跨文件区状态 | 文件夹日志状态 | 恢复动作 |
| :--- | :--- | :--- |
| 无条目 | 无条目 | 跳过 |
| 待分发 | 无条目 | 重新分发 |
| 分发中 | 有条目 | 继续完成分发 |
| **转移完成** | 有条目 | 跳过，等待回收 |
| 分发中 | 无条目 | 回滚分发标记 |

**这张表是"权威不对称"规则的表格化表达**（见第 3 点），两者必须一致。
如果实现中发现某一行与不对称规则冲突，**以不对称规则为准**并回头修表。

### 3. 权威判定的不对称层级（最容易实现错的一条）

| 证据组合 | 判定 |
| :--- | :--- |
| 目标侧"已确认接收" | **完整证明**，可单独确立归属 |
| 源侧未抹除 + 目标侧已确认 | **判归目标侧，即刻生效**（源侧未抹除不构成反对证据） |
| 源侧存在 + 目标侧无确认 | 源侧记录**不足以立权**，条目落入模糊地带，交窗口裁定 |

**核心规则：目标侧权威，源侧只是辅证** —— 能补强、**不能否证**。

### 4. 条目级生效 vs 窗口：粒度是条目，不是批次

| 部分 | 判定性 | 生效时机 |
| :--- | :--- | :--- |
| 已完成搬运的条目 | 确定 | **立即**，按可生效的最大范围逐条生效 |
| 归属不明确的条目（模糊地带） | 不确定 | 窗口边界统一裁定 |

**单调安全推进规则**：每个条目一旦可判定就生效，**绝不因为同一批里还有别的
不确定条目而被连坐推迟**。

这条同时消除一个隐患：若整批等窗口，那么"分发长期停在 40%"会让已搬完的部分
**永不生效**。条目级生效下，已搬完的那部分本来就是生效的，只有归属模糊的才进窗口。

### 5. 过半移交：资格与执行解耦

| 事实 | 含义 | 谁读它 |
| :--- | :--- | :--- |
| 已越过半数（`crossed_half`） | **具备移交资格** | 窗口调度器 |
| 已移交（`handed_over`） | 权威方已切、**世代已递增** | 缓存校验、读路径 |

**世代号在移交完成时递增，不在越线时递增。** 越线之后、窗口之前的这段时间里，
权威方**仍然是源侧**——尽管多数条目已在目标侧。

这不是瑕疵，是正确语义：移交完成前，源侧仍是唯一可校验的权威，缓存无需因为
"看起来搬得差不多了"就提前失效。

**移交执行的三个要求**：

1. **条件性原子操作**（典型 CAS：`if 仍具备资格 then 切换权威方并递增目标世代`），
   执行前后归属可判定、可重放。
2. **空窗口完全无操作**——不递增任何世代、不产生任何失效。
3. **移交动作本身留痕**，以便崩溃恢复回答"上一次成功移交发生在哪个窗口"。

### 6. 跨文件区自身的空间管理

- 跨文件区是**有限资源**（256 MB – 1 GB），写满时行为必须定义：
  返回 `NXFS_ERR_CROSSFILE_REGION_FULL`（已在 `nxfs.h` 中定义），**不得静默丢弃**。
- 回收是**后台批量清除**，不是逐条。清除必须在校验"目标侧已确认接收"之后才可进行。
- 跨文件区条目是 `CROSSFILE_ENTRY` 责任主体（`a` = 条目序号），
  因此条目级失效是可能的——这正好支撑第 4 点的条目级生效。

## 常见坑

1. **别让整批等窗口** —— 会破坏"可生效最大范围"，并让已搬完的部分卡住。
2. **别在越线时就递增世代** —— 必须在移交完成时。
3. **空窗口不要产生任何副作用** —— 包括"顺手做点维护"。
4. **源侧未抹除不能当反对证据** —— 这是不对称规则的核心。
5. **不要逐条下发** —— 会退化成随机写，丧失本机制的性能意义。
6. **跨文件区条目要能独立判定归属**（靠条目自身状态），不要用批次进度推断归属。
7. `NXFS_EVENT_CROSSFILE_DISTRIBUTION_PENDING = 4` 是**低优先**（`4 & 1 == 0`）。
   不要误标成高优先，否则会霸占高优先队列。
