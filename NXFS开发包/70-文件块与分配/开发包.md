## 边界（先看这段）

**需要读**：`10-公共约定.md` §3 策略参数、`INV-6`（内核文件豁免迁移）、`INV-8`（紧急保留）；
`40` 的 `EXTENT` 主体接口。

**不需要读**：EFI 驱动、Windows 集成、跨文件区分发细节。

**本包不做**：不做跨文件区（`60`）、不做日志区分配（`50`，那有物理分散约束）、
不做程序文件夹语义（`90`，本包只提供它需要的块级能力）。

## 职责

| 职责 | 说明 |
| :--- | :--- |
| 文件夹块 | 一个文件夹的内容物（数据 + 日志区 + 间隔）作为一个**复合分配单元** |
| 预留 | 按文件大小分档预留，吸收增长、避免碎片 |
| 间隔 | 文件之间的缓冲带，吸收文件增长 |
| 增长处理 | 三档：就地扩展 / 占用间隔 / 块内迁移或拆 extent |
| 封块 | 日志区达阈值或子文件夹数超限时封块 |
| 删除与回收 | 整块蒸发 + 延迟释放 + 紧急保留 |
| 碎片整理 | 块级整理、迁移即整理 |
| 预留回收 | 压缩古旧文件的预留 |

## 关键设计点

### 1. 块结构（设计稿 §5.1）

```
[日志区][文件A数据+预留][间隔][文件B数据+预留][间隔][文件C数据+预留][日志区]
```

注意日志区出现在**两端**。这不是笔误——两端各一份是为了：

- 头簇在块首（便于物理偏移直寻，`50` 的机制）；
- 尾簇在块尾（便于块增长时从尾侧扩展而无需移动已有日志）。

**实现要求**：块头与块尾都要能自验证（各带标识与校验和）。

### 2. 预留量分档（设计稿 §5.1）

| 文件规模 | 预留量 |
| :--- | :--- |
| 小文件 | 64 KB – 256 KB（**固定下限，不是百分比**） |
| 中文件 | 10% – 20% |
| 大文件 | 5% – 10% |

**注意小文件是绝对值而非比例**：小文件按比例算会得到极小值，无法吸收增长。
分档阈值需在实现中固定（建议：小 ≤ 1 MB、中 ≤ 64 MB、大 > 64 MB，与 §6.2 的大文件阈值对齐）。

### 3. 增长三档处理（设计稿 §5.2）

| 增长程度 | 动作 |
| :--- | :--- |
| 预留内 | **就地扩展**，更新元数据（最小代价，无迁移） |
| 用完预留，间隔够 | **占用间隔**（相邻文件需让出缓冲带） |
| 间隔不够 | **块内迁移** 或 **拆 extent** |

**实现纪律**：

- 前两档**不得产生迁移**（`WriteResult.migrated == 0`）。迁移是昂贵操作，
  能就地就就地。
- 第三档的两种选择对应不同的写模式，已在 API 表达：
  `NXFS_WRITE_IN_PLACE_ONLY`（不允许迁移，空间不足即失败）、
  `NXFS_WRITE_ALLOW_MIGRATION`、`NXFS_WRITE_ALLOW_SPLIT`。
  **由调用方选择**，本包执行——不要自行升级到允许迁移。
- 发生迁移时必须回报 `new_subject`（主体已变），否则调用方持有的旧主体会失效而不知情。

### 4. 封块条件

- 日志区达阈值，或
- 子文件夹数超限。

封块后新内容进入新块。**封块是正常行为，不是错误**——不要把它当失败返回。

### 5. 删除与回收：三级流程（设计稿 §7.1）

| 步骤 | 动作 |
| :--- | :--- |
| **即时** | 父日志标记"子树 X 待删除"，**回报用户** |
| **后台渗透** | 逐层向下标记，按文件夹批量回收 |
| **空间回收** | 顶层 extent **整块蒸发**，按 extent 批量释放 |

**这条路径的性能收益来自"即时回报 + 后台批量"**（设计稿 §16 声称"5 万文件秒级回报"）。
实现要求：

- 即时步骤**只标记**，不遍历子树——遍历放后台，否则"秒级回报"不成立。
- 回收按 **extent 批量**更新空闲位图，不是逐簇。
- 顶层 extent 按文件夹聚合，因此"整块标记待回收"是一次操作，而不是 N 次。

### 6. 延迟释放（设计稿 §7.3）

- 被标记待删除的簇状态为 **"延迟释放"**。
- **新写入优先使用真正空闲的簇** —— 这是为了避免"刚删的数据马上被覆写"导致
  正在读的句柄读到新数据（POSIX `unlink` 后仍可读的语义基础）。
- 系统保留 **5% 紧急空闲空间**（`INV-8`：常规写入不得占用）。

三种簇状态要分清：**空闲** / **延迟释放** / **已分配**。新写入只看"空闲"。

### 7. 碎片整理

#### 7.1 迁移即整理（设计稿 §8.1）

从其他文件系统迁入时：目标盘**自上而下构建**，文件夹分配连续区域，文件按源顺序写入。
迁入完成后**天然紧凑，无需整理**。

**这是最重要的"不做"**：迁入路径不要调用整理逻辑，也不要按随机顺序写文件。
实现了正确的迁入顺序，就等于免费获得了一次全盘整理。

#### 7.2 块级整理（设计稿 §8.2）

| 触发条件 | 动作 |
| :--- | :--- |
| 块内碎片率 > 阈值 | 选定块，找连续空闲区域 |
| 系统空闲 + 空间压力低 | 顺序写入新区域 |
| 写入热点集中 | 更新父日志偏移，旧块标记待回收 |

**实现要点**：

- 整理时**锁定块**，新写入**路由到新块**（不是等锁）。
- 更新父日志偏移后，旧块标记待回收——**偏移更新必须先于旧块释放**，
  否则中断后出现悬空引用。
- 与压缩协同：压缩后数据变小，可原地重写或迁移到更小连续区域。

#### 7.3 ⚠️ 内核文件豁免迁移（`INV-6`，硬约束）

**可引导卷上，引导文件表所指的文件豁免物理迁移。** 这是**卷级不变量**，
不是调用方可选项：

```c
/* 可引导卷上此值被强制为 0 */
uint32_t allow_kernel_file_move;
```

**理由**：设计稿 §6.2 允许大文件独立成块，§8.2 允许块级整理"更新父日志偏移"。
若内核文件也被迁移，则下次冷启动时阶段一按**总账记载的 LBA 直读**会读到
**已蒸发或已复用的块**。

**为什么选"豁免迁移"而不是另外两种方案**：

| 方案 | 固件侧新增逻辑 | 失败面 | 结论 |
| :--- | :--- | :--- | :--- |
| **内核文件豁免迁移**（采用） | 零 | 最小 | ✅ |
| 迁移后同步回写总账 | 需校验总账 + 处理部分写入 | 中：回写本身可能遇到"完整性不确定" | 备选 |
| 引导表改指间接层 | 需多一次跳转解析 | 大：固件侧引入新结构 | 不采纳 |

好处是**数据盘完全不受此约束**——只在可引导卷上多一条约束，块级整理逻辑不必全局变复杂。

### 8. 预留回收（设计稿 §5.3）

| 项 | 值 |
| :--- | :--- |
| 触发 | 预留浪费率 > **30%** |
| 动作 | 压缩古旧文件预留，空间归还块空闲池 |
| 古旧定义 | > **6 个月**未修改 **且** 预留使用率 < **20%** |

**两个条件是与关系**，必须同时满足。只看时间会把长期运行的程序文件误判为古旧。

## 常见坑

1. **小文件预留是绝对值**（64 KB–256 KB），不是百分比。
2. **不要自行升级写模式** —— 迁移开销由调用方决定是否承担。
3. **删除的即时步骤只标记**，遍历必须放后台，否则拿不到"秒级回报"。
4. **回收按 extent 批量**，不要逐簇更新位图。
5. **"延迟释放" ≠ "空闲"** —— 新写入只能看空闲。
6. **紧急保留 5% 不可被常规写入占用**，要在分配前检查。
7. **偏移更新必须先于旧块释放**，否则中断后悬空。
8. **可引导卷上内核文件不迁移**（`INV-6`），且这条**不可被调用方关闭**。
9. **预留回收的两个条件是与关系**。
10. **迁入路径不要调整理** —— 顺序写入本身就是整理。
