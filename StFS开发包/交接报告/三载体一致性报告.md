## 0. 一句话结论

**三载体结论一致**：同一组测试源在**宿主 x86_64（Windows）/ Linux x86_64 客机 / Linux aarch64
客机（弱内存序）** 上跑出来的结果**不只是"退出码都是 0"**——包 40 与包 05 两个套件的
**整份输出逐字节相同**（md5 三者相等），且包 40 的 `782 项检查 / 0 项失败` 三个载体完全一致。

**负对照（去掉屏障 ⇒ 期望观察到不一致）在"本载具"上动态打不出来，如实记为未复现**——
按任务要求**不把它说成通过**，机理与证据见 §4。

## 2. 一致性口径：为什么这比"退出码都是 0"强

"退出码都是 0"是最弱的一致性证据（一个什么都不打印、永远 `return 0` 的测试也能满足它）。
本矩阵把口径提到**字节级**：每套件在客机上就地算 `md5sum` / `wc -c` / `wc -l` / `grep -c '^FAIL'`，
宿主侧用同一段字节流在 Python 里算同样的量，然后**逐字段比对**：

| 比对字段 | 宿主 A | 客机 B | 客机 C | 一致？ |
| :-- | :-- | :-- | :-- | :-- |
| `40` 输出 md5 | `9aad743f13739484016f05c593927fe0` | **同** | **同** | ✅ 逐字节相同 |
| `40` 字节数 / 行数 | 982 / 15 | **同** | **同** | ✅ |
| `40` 检查数 / 失败数 | 782 / 0 | **同** | **同** | ✅ |
| `40` AC 标记数 | 10 | **同** | **同** | ✅ |
| `40` `^FAIL` 行 | 0 | **同** | **同** | ✅ |
| `05` 输出 md5 | `1c8f01cb5c90b09049c611f6ee051038` | **同** | **同** | ✅ 逐字节相同 |
| `05` 字节数 / 行数 | 659 / 1 | **同** | **同** | ✅ |
| `05` `^FAIL` 行 | 0 | **同** | **同** | ✅ |

**一致性结论**：`40`、`05`、`wm` 三个套件在 **A/B/C 三载体上判定一致**（`wmr` 只在 B/C 跑，
也一致）。**没有任何一项差异**，因此本次没有"最小复现"可写；脚本里的一致性判定分支若
遇到差异，会直接打印 `字段 不同：A=…、B=…、C=…` 并给出复现命令。

客机环境事实（从串口日志里取的，不是猜的）：

| 载体 | `uname -m` | 核数 | 发行版 | 加速器 | QEMU 退出码 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| B | `x86_64` | 4 | Alpine 3.24.2 | `whpx`（硬件加速） | 0（`poweroff` 后干净退出） |
| C | `aarch64` | 4 | Alpine 3.24.2 | **无 `-accel`（TCG）** | 0（`poweroff` 后干净退出） |

> **勘误（不许静默）**：`carrier-evidence/matrix.json` 里 `carrier_runtime.C.accel` 现在写的是
> `"whpx"`，**这是第一版脚本的标注 bug**——aarch64 载体的 QEMU 命令行**根本没有 `-accel` 参数**
> （Windows 上没有 KVM），实际走 TCG。脚本已修（现在按架构算真实加速器，并把 QEMU argv 一起写进
> 证据），但**证据文件没有被重跑覆盖**：重跑需要再开两个 QEMU，而当时工作区里已有**编排方自己的
> 门禁在跑**（见 §5 注），按"一次只跑一个 guest"的纪律本子代理没有抢跑。
> 以**串口原始日志**（`B.serial.log` / `C.serial.log`）与上表为准。

## 3. 弱内存序专项：器具

### 3.1 用的是 StFS 的**公开接口**，不是自建替身

包 80（翻译层与热缓存）的 `stfs_translate.h` §8 **公开声明**了数据面 ring 的两条内存序契约：

> ① **只有 `COMMITTED` 的槽位可见**；之前的内容一律不可读（防读到**撕裂的元数据**）；
> ② 生产者以 **release** 语义发布 `COMMITTED`，消费者以 **acquire** 语义读取。

而 `ring.c` 顶部自己写着：

> **内存序**：生产者以 release 发布 `COMMITTED`，消费者以 acquire 读取。**注意**
> "在弱内存序架构上验证"是 AC-80.8 的要求，属**人工/ARM 环境**，x86_64 通过不构成证据。

`wm` 套件就是**把这句话变成可重复证据**：真跑 `stfs_tl_ring_produce_begin` /
`stfs_tl_ring_produce_commit` / `stfs_tl_ring_consume` / `stfs_tl_ring_ack`（**链接 `ring.c` 本体**），
一个生产者线程 + 一个消费者线程：

* 载荷 512 字节（64 个 64 位字），每个字的期望值 = `wm_word(seq, i)`（只由序号与下标决定，
  **无法被上一轮的陈旧内容巧合命中**）；
* 消费者**只在 acquire 读到 `COMMITTED` 之后**才读载荷，逐字核对；
* 任何"看到 `COMMITTED` 却读到不完整/错序载荷"都计一次违例，并记录 `seq/off/got/want`
  以便给最小复现。

### 3.2 静态证据（不依赖运行期，可重复）

`zig cc -target aarch64-linux-musl -O2 -S` 摊开汇编，数**屏障指令在 / 不在**：

| 被测函数 | aarch64 汇编里的屏障指令 | 结论 |
| :-- | :-- | :-- |
| `stfs_tl_ring_produce_begin` | 2 条 | 有 |
| `stfs_tl_ring_produce_commit`（release 发布 `COMMITTED`） | 2 条：`ldar w9,[x9]` / **`stlr w10,[x9]`** | 有 |
| `stfs_tl_ring_consume`（acquire 读） | 1 条：**`ldar w10,[x10]`** | 有 |
| `stfs_tl_ring_ack` | 2 条 | 有 |
| `wm_probe` 的 **POS**（配对正对照）`np_producer_pos` / `np_consumer_pos` | 2 条 / 2 条（`stlr`、`ldar`） | 有 |
| `wm_probe` 的 **NEG**（负对照，故意去屏障）`np_producer_neg` / `np_consumer_neg` | **0 条 / 0 条** | **没有**（正是"把屏障删掉"） |
| `wm_probe_relaxed`（`-DWM_FORCE_RELAXED`，连 POS 也降级） | POS **0 条** | 对照成立 |

> 这条证据的意义：它证明**负对照是"真的没有屏障"，而不是"改错了没编出来"**；
> 也证明"有屏障"的那一版在 aarch64 上确实落成了 `stlr`/`ldar` 指令（x86_64 上
> release/acquire 是普通 `mov`，这条差异只有换了目标架构才看得见）。

## 4. 弱内存序专项结论（正对照 ✅ / 负对照 ❌ 未复现）

### 4.1 正对照：**有屏障 ⇒ 一致**（在 aarch64 上成立，可重复）

| 载体 | `wm` 轮数 | 完成轮数 | ring 违例 | 接口失败 | 首个违例 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 宿主 x86_64 | 20000 | 20000 | 0 | 0 | 无 |
| Linux x86_64 客机 | 20000 | 20000 | 0 | 0 | 无 |
| **Linux aarch64 客机** | 20000 | 20000 | **0** | **0** | 无 |

* `WM_RING_DONE == WM_RING_ITERS == 20000` 是**有牙判据**：证明两线程真的跑完，不是空转骗绿；
* 消费者逐字核对了 20000 × 64 = **1 280 000 个载荷字**；
* ⇒ 包 80 声明的 release/acquire 契约，在**弱内存序架构 aarch64** 上的多核压力下成立。

### 4.2 负对照：**去掉屏障 ⇒ 期望观察到不一致——本载具上打不出来（如实记录为未复现）**

负对照与正对照**逐行同构**（同样的结构、同样的压力、同样的 300000 轮），唯一差别是：

* POS：`__atomic_store_n(&flag, r, __ATOMIC_RELEASE)` / `__atomic_load_n(..., __ATOMIC_ACQUIRE)`；
* NEG：`__atomic_store_n(&flag, r, __ATOMIC_RELAXED)` / `__atomic_load_n(..., __ATOMIC_RELAXED)`
  （载荷是普通内存写，即"屏障被删掉"的样子）。

实测（三个载体、两个探针二进制、共 5 条流水线）：

| 载体 | `wm` 的 NEG 违例 | `wm` 的 POS 违例 | `wmr`（连 POS 也 relaxed）的 POS 违例 |
| :-- | :-- | :-- | :-- |
| 宿主 x86_64 | 0 / 300000 | 0 / 300000 | （未跑） |
| Linux x86_64 客机 | 0 / 300000 | 0 / 300000 | 0 / 300000 |
| Linux aarch64 客机 | **0 / 300000** | 0 / 300000 | **0 / 300000** |

**⇒ 负对照没有在任何一个载体上复现出"看到发布位但载荷不完整"。这不是"无屏障也安全"的证据，
而是本载具的建模局限。** 机理（两条，都有实测支撑）：

1. **宿主是 x86_64（TSO）**：本例的缺失屏障是**发布位的 StoreStore 次序**（载荷写 → 发布位写）。
   x86 的 TSO **保持 StoreStore 次序**，所以"发布位先可见、载荷没写完"这件事在 x86 上
   **结构上不可能被观察到**——这正是 x86 上不加屏障的代码常常"看起来也能跑"的原因，
   也是 AC-80.8 说"x86_64 通过不构成证据"的原因。
2. **aarch64 客机跑的是 TCG（Windows 上没有 KVM）**：QEMU TCG 把每条 guest 访存展开成
   **多条宿主指令**，`store → load` 之间夹着大段翻译代码，宿主 store buffer 早被排空；
   于是"客机"甚至比 x86 客机**更接近顺序一致**。这条有量化证据 —— 见 §4.3 的 litmus 读数：
   **aarch64 客机 2/4000，x86_64 客机 119/4000**。

### 4.3 载体内存序读数（litmus）：证明"探针不是恒绿"

用经典 **store-buffering (SB)** litmus（`t0: X=1; r0=Y` / `t1: Y=1; r1=X`，两边 relaxed 原子）
量"这个载体到底有多弱"：

| 载体 | SB 违例 / 轮数 | 读法 |
| :-- | :-- | :-- |
| 宿主 x86_64（Windows 原生） | 0 / 4000 | 本机调度窗口太窄，没打着 |
| Linux x86_64 客机 | **119/4000、242/4000**（两次采样） | **探针有牙**：真有 relaxation 时能抓到（≈3%） |
| **Linux aarch64 客机（TCG）** | **2/4000、0/4000**（两次采样） | **比 x86 客机更"强"** ⇒ 证实 §4.2 机理 2 |

> 这条读数同时说明三件事：
> ① 探针**不是恒绿**（B 上打着 119 次），所以"aarch64 上 0 违例"不是空转；
> ② TSO 允许 StoreLoad 放松（所以 SB 能响），但**不允许 StoreStore 放松**（所以 NEG 不响）；
> ③ aarch64+TCG 这个组合**不是合格的弱内存序裁判**。

### 4.4 StFS 有没有"公开的 CPU 内存屏障接口"？——**没有**（如实说明）

任务要求：若 StFS 侧没有合适的公开屏障接口，就如实报告并给建议插入点。逐项查证结果：

| 候选 | 位置 | 是什么 | 能不能用于本专项 |
| :-- | :-- | :-- | :-- |
| `stfs_tl_ring_*`（release/acquire） | 包 80 `stfs_translate.h` §8 | **公开、可测的并发接口**；屏障语义**内嵌在实现里**（`ring.c` 的 `TL_STATE_STORE/LOAD` 宏） | ✅ **可以**——本专项的正对照用的就是它（但它本身不是"屏障 API"） |
| `stfs_st_barrier_fn` | 包 30 `storage.h:215`，由 `stfs_st_flush` 调用 | **设备持久化屏障**（宿主回调，语义 = ATA FLUSH CACHE / fsync），`NULL` 时"可见地降级"（`device_barrier=0`） | ❌ **不能**——它管的是"数据落盘的持久化次序"，**不是 CPU 访存次序**；拿它当 CPU 栅栏是概念错位 |
| `80/ring.c` 的 `TL_STATE_STORE/LOAD` | 包 80 `ring.c:19-20` | `__atomic_store_n/__atomic_load_n`，**文件内宏**，未导出 | ❌ 不可外部调用 |

**结论：StFS 目前没有公开的 CPU 内存屏障 / fence API。** 现有唯一与"屏障"同名的公开面
（`stfs_st_barrier_fn`）是**设备持久化屏障**，不能替代内存栅栏。因此本专项**不能**做到
"让调用方自己插屏障 / 拔屏障"那种对照——它只能在**已有公开接口的语义层面**取证（§4.1），
再加**编译期/ISA 层面的静态对照**（§3.2）。

**建议插入点**（供包 80 / 规范所有人裁定，本子代理**没有**改任何包的头文件或 AC 表）：

1. **最小、最贴现状**：在包 80 的 `stfs_translate.h` §8 里，把 `ring.c` 现在私有的
   `TL_STATE_STORE/LOAD` 提升为一对**带名字的公开语义**，例如
   `stfs_tl_ring_publish_release()` / `stfs_tl_ring_observe_acquire()`（或等价的
   `stfs_tl_ring_fence_publish/fence_acquire`）。收益：内存序契约从"注释里的承诺"变成
   **可被外部测试直接调用的面**，本 `wm` 探针就能做"同一段代码、插/拔该调用"的**同源对照**，
   负对照的动态复现就不再依赖"换一台真 ARM 机器"。
2. **通用层**：若将来别的包也要栅栏，在 L1（`stfs.h`）或包 30 定义一个
   `stfs_memory_fence(stfs_fence_kind_t)`，语义写死为 C11 `atomic_thread_fence` 的
   `release/acquire/seq_cst` 三档，并明确"freestanding 下用 `__atomic_*` 内建实现"。
   注意别和既有的 `stfs_st_barrier_fn`（**设备**持久化）同名或混义。
3. **顺带**：`stfs_st_barrier_fn` 的文档里可以加一句"**这是设备持久化屏障，不是 CPU 内存栅栏**"，
   避免后来者误用（本次查证时第一眼就容易把它当成"屏障接口"）。

### 4.5 对 `AC-80.7` / `AC-80.8` 的影响（**只报事实，不改状态**）

包 80 的 `README.md` / `FREEZE.md` 现在把 `AC-80.7` 的**并发半**与 `AC-80.8` 记为
**"必须由人在 ARM 环境验；x86_64 通过不构成证据"**。本专项的实际增量是：

* ✅ 把"ARM 上的多核压力夹具"从**没有**变成**有**（`verify/carrier_matrix.py` 的 `wm` 套件，
  aarch64 客机 + 4 核 + 真 StFS `ring.c` 本体 + 20000 轮 SPSC + 逐字核对载荷）；
* ✅ release/acquire 契约在 aarch64 上**没有观察到撕裂读 / 错序**（正对照通过）；
* ❌ **但仍不能宣告 `AC-80.8` 具备**：因为(1)本载具是 QEMU/TCG，不是真 aarch64 硅片；
  (2)"去掉屏障 ⇒ 能观察到不一致"的**负对照没有打出来**（§4.2）。判据的"有牙"要求没满足，
  所以**本子代理不改这两条 AC 的状态**，只把证据交给包 80 的所有人去裁。

**要在本专项上把 `AC-80.8` 真正做实的建议**（按性价比排序）：

1. **真 aarch64 机**（一块树莓派 4/5 或任意 ARM64 板子，Linux + `gcc -O2`）跑同一个
   `wm_probe.c`：预期 POS 0 违例、**NEG > 0 违例**，正负对照一次到位。成本最低、说服力最高。
2. **aarch64 宿主上的 QEMU**（或 `qemu-system-aarch64 -accel kvm` 于 ARM Linux）：
   此时 TCG 的宿主内存序不再是 TSO，§4.2 的机理 2 消失，负对照有机会复现。
3. **内存模型检查器**：把 `ring.c` 的 release/acquire 抽象成 herd7/`rmem` 的 C11 litmus，

## 7. 怎么复现（一条命令）

```powershell
$env:PYTHONIOENCODING='utf-8'
$env:ZIG="F:\Workspace\.tools\ziglang\zig.exe"
python -u verify\carrier_matrix.py               # 三载体：40 / 05 / wm（B、C 另跑 wmr）
python -u verify\carrier_matrix.py --carrier C   # 只跑 aarch64 弱内存序载体
python -u verify\carrier_matrix.py --suite wm    # 只跑弱内存序专项
```

退出码：**三载体结论一致 ⇒ 0**；有差异或某载体没跑成 ⇒ 非 0（`--allow-partial` 可放宽，
但脚本**默认不放宽**，免得把"没跑成"混成"通过"）。

脚本自带的防假绿措施（都来自既有器具的实测教训）：

* 取件/完成标记一律用**算术展开**（`echo FETCH_x_$((6*7))_OK`、`echo DONE_$((3*9))_x`）——
  串口会**回显命令行**，朴素的 `echo FETCH_OK` 会假绿；
* 客机侧先 `ip link set eth0 up` + `udhcpc`（Alpine virt ISO 默认不配 eth0）；
* 每个套件都要求 `WM_RING_DONE == WM_RING_ITERS` / 见到 `^FAIL 行数` 等**有牙**字段；
* 跑完 `poweroff` 并断言 **QEMU 退出码 == 0**，未干净退出会在日志里写出来。
