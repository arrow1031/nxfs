# 跨版本兼容矩阵（演练实测报告）——玩法 1

> 批准口径：只出证据、不动生产代码、不跑门禁。
> 本报告全部结论来自**实测原始输出**（`logs/` 下 16 个逐次日志 + `rehearse-run.log`）。
> 演练脚本：`rehearse_compat.py`；旧读者构建：`prep_old_tree.py` + `build_old_reader.py`。

---

## 0. 一句话结论

1. **没有一格"静默误读"**：16 个组合里，凡不兼容者都以 **`mount(read-only) rc=-6 CORRUPT`** 或
   **"挂载成功但 `tables_present=0` + 读路径 `rc=-40`"** 收场，没有"当成正常卷少看/错看"的情况。
2. **最重要的缺口**：**新读者读不了旧卷**（`OLD 卷 + 新读者 + 未 poke` ⇒ `rc=-6`），
   而批次任务书 §2.1 明确要求"**旧 v1（单簇 32 条）继续可读**"。根因见 §4。
3. **裁定设想的"`version=2` 明确表态"并不是今天真正起作用的门**：新卷没有任何版本标记时，
   旧读者就已经 `rc=-6`；让它拒收的是**表容器头的 capacity 字段不相等**（旧 32 / 新 4096）。
4. **旧读者遇到版本标记不是"拒挂载"，而是"降级"**：`mount rc=0` + `tables_present=0` +
   总账自述四字段全 0 + 读路径 `rc=-40`；同时**旧工具的 `ledger_result: OK` 汇总行是假的**
   （本批已在新工具里修掉）——"静默"只发生在这条汇总行上。

## 2. 方法（为什么这样才可信）

- 镜像：128 MiB 分区（`--start-lba 2048 --count-sectors 262144`），
  由**该属主自己的** `d0_mkfs` + 工具写入：`mkdir /d` + `create /d/f1..f3`（期望 `ls /d = 3`）。
  两个属主各自一份 **master**，此后**只对副本操作，master 永不修改**。
- 三组独立 poke（每组一份新副本）：
  - `P1` `ext.version = 2`（两副本 × 两槽，**重算扩展 CRC**，覆盖 `[0,216)`）；
  - `P2` `ext.format_flags = 1`（bit0；同上重算 CRC）；
  - `P3` **对象头 `version = 2`**：改完重算**对象头 CRC**（头 `[0,68)`）**与簇头 CRC32C**
    （覆盖簇 `[8, cluster_size)`）——不重算就会变成"校验和失败"，那是假阳性。
  - `P0` 基线（不 poke）作为对照。
- 对象头定位**不靠几何算术**：在镜像里搜 `STFS_META_OBJECT_MAGIC` + `struct_size=72` +
  `kind=1(主体表)`；因为 CoW 旧版本仍在盘上（实测 5 个候选），活的那份再按**当前扩展槽
  （两槽取 `txn_id` 大者）自述的簇号**筛出（`rehearse-run.log` 里逐候选打印，可复核）。
- 每个 (镜像副本 × 读者) 跑三条命令：`probe`（只读挂载）、`ledger`（只读挂载 + 总账核验）、
  `ls /d`（读路径；**注意：本工具的 `ls` 会 rw 挂载并在 `tables_present=0` 时按需建表**，
  故它只用于判定"读路径是否给出分类错误"，不当作零写证据）。
- 判定六类（口径写进脚本）：`CRASH` / `REJECT-MOUNT` / `DEGRADE-TABLES` /
  `ACCEPT-CONSISTENT` / `SILENT-MISREAD` / `SILENT-UNKNOWN`。**本轮没有 CRASH，也没有
  SILENT-MISREAD / SILENT-UNKNOWN。**

## 4. 逐条发现（含根因与代码位置）

### 发现 1（最重要，缺口）：新读者读不了旧卷
- 证据：`OLD + P0 + NEW` ⇒ `mount(read-only) rc=-6 (CORRUPT)`（原始日志
  `logs/OLD-P0-none-NEW.log`）。
- 根因（**已用反证实验证明，不再是推断**）：`40-元数据引擎/cow.c:91`
  `if (head->capacity != expected_capacity) return STFS_CORRUPT;` —— **要求逐字相等**，
  而旧卷盘上 `capacity=32`、新实现常量 `4096`。
- **反证实验（`prove_capacity_gate.py`，日志 `logs/OLD-F1-capacity4096-*.log`）**：
  取旧卷副本，**只把活表容器头的 `capacity` 从 32 改成 4096**（其余字节一个不动，
  仅重算该簇簇头 CRC）：
  | 读者 | 结果 |
  | :--- | :--- |
  | NEW | `mount rc=0`、`tables_present=1`、`ls /d = 3` ⇒ **ACCEPT-CONSISTENT** |
  | OLD | `mount rc=-6` ⇒ REJECT-MOUNT（它要求 capacity==32） |
  ⇒ 同一个镜像、同一个字段，两边一读一拒：**capacity 逐字相等就是唯一的兼容门**
  （也再次说明今天起作用的不是 `version` 表态）。
- 与任务书冲突：批次任务书 §2.1 要求"旧 v1（单簇 32 条）**继续可读**"；现实现不满足。
- 机理补充：旧格式把**整表**写盘（`payload_len = 48 + capacity×entry_bytes = 3888`，实测），
  新格式按 `count` 只写已用前缀（实测 `768 = 48+6×120`）。因此"接受已用前缀"这条兼容性
  只覆盖了**编码长度**，没有覆盖**旧卷的 capacity 值**。
- 处置建议（属主流 API 批，我不改）：读取侧应**按盘上 `capacity` 解释**该卷的行数权威，
  并在"盘上 capacity 大于本实现容量"时**明确拒收**（分类错误码）；不要要求与编译期常量逐字相等。

### 发现 2：`version=2` / `format_flags` 表态下，**旧读者是"降级"不是"拒挂载"**
- 证据：`OLD + P1/P2 + OLD` 与 `NEW + P1/P2 + OLD` 都是 `mount rc=0`、`tables_present=0`、
  自述四字段 `0/0/0/0`、读路径 `rc=-40`。
- 这是**设计口径**（"扩展不可信 ⇒ 挂载成功但表不可用"），**不是静默**：字段和读路径都有分类信号。
- 但要指出的两点：
  1. 裁定原文要求"旧读者**明确拒收**而非静默误解"。按机制看这是"**明确降级**"；
     是否算达标，是**策略判断**，需要主流定（我按事实呈现，不替它下结论）。
  2. **旧读工具的汇总行是假的**：自述四字段全 0 时它照样打印 `ledger_result: OK`
     （只按返回码判定）。只看汇总行的调用方会**漏判**——这正是本批在**新工具**里修掉的那个缺陷
     （见 `60eb988`）。**旧二进制没有这个修复**（它是 `14588fe` 的产物）。

### 发现 3：对象头 `version` 是最强、最一致的门
- `P3` 在**所有四种** (属主×读者) 组合下都是 `REJECT-MOUNT rc=-6`。
- 机理：`cow.c:39/85` `if (head->version == 0 || head->version > STFS_META_FORMAT_VERSION) ⇒ CORRUPT`。
- 含义：如果 v2 格式只改"表对象怎么排布"，**用对象头 `version` 表态就已经足够让旧读者拒收**，
  不必依赖 capacity 不等这种"隐式"差异。

### 发现 4：今天的"跨版本拒收"是**隐式**的（capacity 不等），不是裁定的**显式**表态
- 证据：`NEW + P0 + OLD`（新卷无任何版本标记）⇒ 旧读者就已经 `rc=-6`。
- 含义：容量批把 `SUBJECT_CAPACITY` 抬到 4096，无意间让新卷对旧读者"必然不可读"；
  这**碰巧**满足了"旧读者拒收"，但**不是** `version=2` 语义，且**没有任何可读的诊断**
  （输出只有 `rc=-6 CORRUPT`，看不出是"版本不兼容"还是"盘坏了"）。
- 建议：v2 落地时把"版本不兼容"与"介质损坏"**分成两个错误码**（或让 `ledger/probe` 打印
  "盘上格式版本=N，本实现支持≤M"），否则现场只会看到 `CORRUPT`。

### 发现 5：新读者对 `ext` 不可信的处理比旧读者更严（**未定位到提交**，如实登记）
- 证据：同一张 `NEW + P1` 副本，旧读者 `mount rc=0`（降级），新读者 `mount rc=-6`（拒挂载）。
- 我的排查：`14588fe..HEAD` 范围内 `ledger.c` 只有 `dd8e1b1` 动过，而它改的是
  `led_table_load_one` 的**载荷长度校验**与 `progress_query`，**没有动扩展有效性/挂载决策**；
  `tools/stfs_use.c` 的挂载路径与旗标也没变（只有注释与我那几处修复）。
  ⇒ **我没有 bisect 出根因**，只登记"行为不一致"这一事实，不做推测。
- 影响：若 v2 想走"降级可读"路线（旧读者行为），新实现当前会**拒挂载**；
  反过来若 v2 想要"拒挂载"，旧读者做不到。**两边必须先统一口径**——这正是主流 API 批要定的事。

## 5. "拒收"是否成立？——按批准口径的判定

| 要求 | 实测 | 判定 |
| :--- | :--- | :--- |
| 旧读者遇到新格式必须**明确错误码** | 有：`rc=-6 CORRUPT`（P3、以及新卷本身） | ✅ 成立 |
| 旧读者**不崩溃** | 16 格里无崩溃标记、无异常退出码 | ✅ 成立 |
| 旧读者**不静默** | 字段/读路径都有分类信号；**但** 旧工具 `ledger_result: OK` 汇总行会骗人 | ⚠️ **部分成立**（汇总行是唯一"静默"面，新工具已修） |
| 旧读者必须**拒收**（而非"降级"） | `ext.version` / `format_flags` 下旧读者仍**挂载成功**（`tables_present=0`） | ❌ **不成立**（是"明确降级"，不是"拒挂载"） |
| 新读者读旧卷（任务书 §2.1） | `rc=-6` | ❌ **不成立**（发现 1） |

> 按批准口径第 ④ 条："若拒收不成立 ⇒ **如实上报，不要补丁式修**"。
> 本报告只给事实与建议，**未改任何实现**。

## 7. 未验证项与原因（诚实登记）

- **没做根因 bisect**（发现 5）：只登记行为差异；原因：本批范围外 + 演练纪律"不改代码"。
- **`ls` 不是零写证据**：本工具的 `ls` 会 rw 挂载、必要时建表（日志可见 `tables_created=1`）；
  故"读路径 rc"只用来判定分类，不用于"零写"结论（零写结论在 `probe`/`ledger` 的只读挂载上）。
- **只测了"表对象/扩展"三类标记**，未测：`STFS_META_OBJ_*` 其它对象的 `version`、
  `STFS_META_TABLE_MAGIC` 变更、快照/子卷表标记——如需可加法扩矩阵（脚本已模块化）。
- **镜像规模 128 MiB**（不是 512 MiB）：兼容性与几何无关，缩小只为让 16 份副本快速可复现；
  若要覆盖"副总账远离主总账"的极端几何，可另跑大分区一例。
- 未跑 `verify/gate_all.py`、未用 QEMU、未碰物理盘（按批准口径）。
