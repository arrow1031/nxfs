## 2. 发现的 BUG 清单

本轮脚本覆盖到的所有对抗输入都拿到了**分类错误码**：未发现崩溃、未发现负对照静默通过。

### 2.1 本批**已修**的真缺陷（脚本第 ②/③ 项在修前是红的）

**ADV-2/ADV-3/ADV-4：只读核验路径完全不做引导文件表校验（静默通过）**

- **现象（修前实测）**：把主引导表的一个字节（`LBA 66048 + 8`，原值 `0x78` → `0x87`）改坏，或把 CRC 字段（`+116`，`0x76` → `0x89`）改坏，`stfs_image verify` **返回 0**，输出里**根本没有引导表这一行**；把主/副两份引导表**同时**改坏，仍然 `result: OK`。而脚本侧独立复算 CRC32C 明确算出「不符」——**检测器有牙，只是没人调用**。
- **成因**：`stfs_meta_boot_probe()`（`40/元数据引擎/ledger.c:1118`）本身**有**完整的主→副降级 + 两份皆坏即 `STFS_ERR_CORRUPT` 的校验，但 L1 的只读路径（`tools/stfs_image.c` 的 `cmd_inspect`）**从不调用它**；`stfs_image` 的 `locate_root` 是**扫簇空间找日志头魔数**，不读引导表 ⇒ 整条只读链上没有任何一处碰过引导表。
- **影响**：引导文件表是**盘上冻结结构**（`20/stfs_disk_layout.h` 的 `stfs_disk_boot_table_t`：固定 4 条 `{lba, size_bytes, crc32c, role}` + 独立 CRC32C）。一个字节被打坏且落在条目的 `lba`/`size_bytes`/`crc32c` 上时，**取卷信息一路成功**，但引导路径（B0/固件）会按被篡改的 `lba` 去读内核载荷，或按被篡改的 `crc32c` 判正误 —— 这是“发现时机最晚、代价最高”的一类静默损坏。
- **最小复现**：
  ```powershell
  $PY='F:\DSH\dsh-home\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe'
  # 造一个带内核载荷的卷，然后只改引导表条目[0].lba 的首字节
  python -c "...format bootproof.img --kernel k.bin; 在偏移 66048*512+16 处 xor 0xFF..."
  stfs_image verify bootproof.img     # 修前：rc=0，输出无 boot_table 行
  ```
  （`verify/adversarial_e2e.py` 的第 ②/③/③b 项即自动化版本，见上文逐项表。）
- **处置（本批已修，加性）**：`tools/stfs_image.c` 的只读核验路径**追加**`stfs_meta_boot_probe()` 调用并打印 `boot_table:` 一行：主表不可信 ⇒ 降级到副表（`from_secondary=1`，**降级可见**）；两份都不可信 ⇒ `bad=1` ⇒ `verify` 退出码非 0。**没有改动任何库代码**（40 的校验本来就是对的），只补上“调用”这一环。
- **修后实测**：
  · 主引导表改一个字节 ⇒ `boot_table: ok rc=0 entries=0 kernel_entries=0 bootable=0 from_secondary=1`（降级可见）；
  · 引导表 CRC 字段改一个字节 ⇒ 同上（`from_secondary=1`）；
  · 主/副**同时**改坏 ⇒ `boot_table: FAILED rc=-6`（`STFS_ERR_CORRUPT`）且 `verify` 退出码 **1**（不假装可用）。

## 3. 未覆盖项与原因

- **掉电项的覆盖缺口**：所有轮次都没能在进程运行中强杀（`format` 首次写盘出现在 0.1–0.3 ms，而 `taskkill /F` 有几十毫秒固定开销）⇒ 只证明了『掉电后结论自洽 + 两种结局都出现』，**未能**证明『两条盘写之间的撕裂窗口』。替代覆盖＝第 1 项的确定性注入（主总账损坏 ⇒ -100 降级可见；主副引导表同时坏 ⇒ -6 且退出码非 0）。要真正覆盖撕裂窗口，需要『可注入失败的设备 vtable』这等新器具。

### 3.1 掉电项的**诚实边界**

`format` 与写负载在本机都是**毫秒级**完成（实测：128 MiB 格式化首次写盘出现在 0.1–0.3 ms 量级），而 Windows 的 `taskkill /F` + 进程回收有几十毫秒的固定开销 ⇒ 本轮**没有任何一轮**真的把进程杀在“两条盘写之间”。
因此本项**证实了**：

1. 掉电后的镜像**结论自洽**（连跑两次 `verify` 结果一致、SHA-256 连续相同、`info`/探针都不崩溃）；
2. 存在**明确的两种结局**（可用 `rc=0` / 失效 `rc!=0`），没有“看似成功”的半成品；
3. 掉电镜像上的只读面**不崩溃**（探针 11 项逐条跑过）。

本项**未能证实**（诚实列出）：真的撕裂写窗口（两条盘写之间掉电）。
**替代覆盖**：该窗口的后果（主总账半写 / 引导表半写）已被第 1 项用**确定性注入**覆盖 —— 主总账改一字节 ⇒ `LEDGER_PRIMARY_CORRUPT(-100)` 且降级可见；主副引导表同时坏 ⇒ `CORRUPT(-6)` 且退出码非 0。要真正覆盖撕裂窗口，需要“按 IO 边界注入故障”的宿主层（例如可注入失败的设备 vtable），那是 L1.5 之外的新器具。

| 顺序 | 动作 | 护栏 | 期望 | 是否写盘 |
| :-: | :--- | :--- | :--- | :--- |
| 1 | `d0_mkfs --whole-disk --disk N --probe-only` | 白名单 + 四判据 + **魔数打点读回** | `guard: ALLOW` 且 `probe: readback MATCH` | **会写**（1 个扇区的打点魔数） |
| 2 | `d0_mkfs --partition --disk N --verify-only` | 白名单 + 四判据 | 只读挂载校验通过（或如实报错） | **不写** |
| 3 | `d0_mkfs --whole-disk --disk N --count-sectors <真实容量>` | 全链 | `D0_MKFS_OK` + 自验 `valid=1 / ext_valid=1 / boot_table rc=0` | **写** |
| 4 | `d0_mkfs --partition --disk 0 --verify-only`（**未授权盘号**） | 白名单 | `DENY_DISK_NO`，**未开可写句柄** | **不写** |
| 5 | `d0_mkfs --whole-disk --disk N --expect-serial <错值>` | 四判据（序列号**不在**判据内） | **WARN 但放行**（见下方「未闭合」） | 视子命令 |
| 6 | 断线/换盘后重跑第 1 步 | 四判据（盘号会漂移、Model 不会） | 判据不中即 `DENY_*`；毒盘命中 `DENY_BLACKLIST` | 不写 |

**上机前置**（与 `StFS开发包/交接报告/真盘首用-runbook.md` 一致）：提权；`--disk N` 指**新插入的机械盘**；`--expect-serial` 与实测对拍；**Boot/System 盘一律拒**；写前魔数读回必须 MATCH。

**上机项里的未闭合点（本批记录，**不判红**）**：`stfs_physdisk.h` 明写『序列号不一致只 WARN 不拦——四判据不含序列号』，而运行手册把 `--expect-serial` 列为硬闸。⇒ 若真机验收依赖『序列号不符即拒』，该判据需要**从 WARN 升级为 DENY**（改动点：`tools/stfs_physdisk.c` 的 `stfs_phys_guard()`）。此外 `--probe-only` 仍会**写 1 个扇区**（打点魔数）——若要求『零写核身』，需要新增一个**不写**的核身子命令。
