# SSD 可用性小优化方案（**待 HDD 主线完事后再做** · 2026-09-29）

> 用户要求：**保持设计思想**、**不放弃已有安全性优势**、**只做小优化**，目标不是"快"，而是
> **"不比 NTFS 差"** 就算达标；**不立即做**，等 HDD 这边完事。
> 前置定性：一期范围是 HDD（SSD/NAND 不碰）⇒ 本方案是**为将来留的口子**，不改一期承诺。

## 0. 一句话立场

**安全性一个字节都不让**：CoW、元数据日志、主副双总账、逐簇 CRC32C、原子事务提交
**全部保留**；下面 6 项改的都是**"怎么和盘说话"**（I/O 策略）、**"什么时候告诉 SSD 哪些块没用了"**（TRIM）、
**"簇怎么挑"**（分配局部性）与**"默认参数"**，**不触碰盘上安全结构** ⇒ 崩溃一致性语义不变 ✓。

## 1. 六项小优化（按性价比排序）

| # | 改动 | 为什么是"小"改 | 保住的安全性 | 预期效果 |
| :--- | :--- | :--- | :--- | :--- |
| **S1** | **连续段批量化 I/O**：链上相邻簇**合并成一次** `stfs_st_read/write`（30 层本就收 `(offset,len)`） | **零格式改动**，只改调用方式 | 逐簇 CRC 仍在（30 层重封簇头）✓ | **单项收益最大**：大文件顺序从"每簇一次往返"⇒ 接近设备速度 |
| **S2** | **TRIM / UNMAP**：① 格式化时整卷 discard；② **提交后**对已释放簇发 discard（对齐、成批） | 设备层加一条可选回调（无该能力时降级为空操作） | **只在事务提交之后**丢 ⇒ 崩溃语义不变 ✓ | 免 FTL 内部 GC 放大、免"越用越慢"、保寿命 |
| **S3** | **默认簇调大 + 分配局部性**：SSD 卷默认 16 KiB（已支持，纯策略）；位图分配按**局部段**优先 | 参数与策略各一处 | 分配仍走同一契约 ✓ | 每字节的元数据次数、链节数同步下降 |
| **S4** | **元数据事务合并**：同一批小操作（如批量建文件、连续小写）**并进一个事务**提交，减少"每次一提交" | 复用既有 `batch_open` 方向 | 事务边界仍原子 ✓ | 小写放大从 ~4–8× 压到 ~2–3×（≈ NTFS 量级） |
| **S5** | **CRC32C 硬件路径全开**（SSE4.2 / ARM CRC 指令），软算作回退 | 少量分支与编译期判定 | 校验强度不变 ✓ | 高吞吐下校验不再成为 CPU 上限 |
| **S6** | **运行长度提示**：块头里已有 `used`/末块标志；**加一个"本段连续簇数"字段**（或复用 `block_count` 语义）供 S1 直接拿到段长 | 块头**加字段**（需版本/标志位配合，属本方案里唯一动到格式的一项） | 结构自洽校验照旧 ✓ | 让 S1 不必"逐块探路"就能一次读大段 |

**可选 S7（不做也不影响达标）**：稀疏/零检测（不落零页）⇒ 直接省写放大。

## 2. "不比 NTFS 差"的判据（可度量，等做时逐条验收）

| 维度 | NTFS（SSD 上） | 本方案后 StFS 目标 | 依据 |
| :--- | :--- | :--- | :--- |
| 大文件顺序读/写 | 接近设备带宽 | **≥ 设备的 70–80%** | S1(+S6) 把 I/O 变成大段 |
| 4 KiB 随机写写放大 | 约 2–3×（元数据日志） | **≤ 3×** | S4 事务合并 + S3 簇调大 |
| 长期不退化 | 有 TRIM | **有 TRIM** | S2 |
| 崩溃一致性 | 元数据日志 | **CoW + 元数据日志 + 双总账（更强）** | 不变，仍是一期优势 |
| 快照/子卷 | 无（VSS 近似） | **近零成本** | CoW 天然 ✓ |

## 3. 明确**不改**的东西（对抗"顺手重构"的诱惑）

- **不**去掉主副双总账（那是抗局部损坏的核心 ✓，且 SSD 上跨全盘双写不再有寻道代价 ✓）；
- **不**把 CoW 换成就地更新（快照/子卷/回滚全靠它 ✓）；
- **不**去掉逐簇 CRC（可检出静默损坏 ✓，硬件路径后几乎免费 ✓）；
- **不**为了吞吐把事务边界放宽到"多操作一提交且可丢"（那正是安全性优势所在 ✓）。

## 4. 落点与风险

- 改动面：S1/S4 在 `40`+`tools` 的 I/O 调用处；S2 在 `20/30` 的设备能力回调；S3 是策略与默认值；
  S5 在 `20/safepath_crc32c.c`（已有 `stfs_cpu_has_sse42()` 先例）；S6 动块头格式 ⇒ **需与 80/EFI/D0 同步**，风险最高 ⇒ 放最后。
- 每项都必须：**加性**、**有牙负对照**、**门禁 40/40 全绿**、**判据只增棘轮只减**。
- 顺序建议：**S1 → S2 → S5 → S3 → S4 →（视需要）S6/S7**。

## 5. 结论

> **可以在完全保留现有安全性的前提下，用 6 项小优化把 StFS 的 SSD 表现做到"≈ NTFS"**：
> 瓶颈原本是"每簇一次同步 I/O"（S1/S6）与"每次操作一提交"（S4），而不是安全设计本身；
> 再补上 TRIM（S2）就不会长期退化。
> **不动安全模型、不动 CoW、不动日志与双总账** ⇒ 一期的安全性优势原样保留 ✓。

## 6. 排期与"不改 HDD 行为"的逐项确认（用户 2026-09-29 决定）

> 用户决定：**SSD 优化直接接在 HDD 真盘实测之后**；并要求"**确认这么做不会出问题**"再动。

| # | 对 HDD 行为的影响 | 安全性 | 结论 |
| :--- | :--- | :--- | :--- |
| **S1 批量化 I/O** | **纯正收益**：把小请求合并成大请求；HDD 顺序读也只是一次更大的顺序 I/O ⇒ 更快 | 逐簇 CRC 与结构不变 | **可直接做** ✓ |
| **S2 TRIM/UNMAP** | **中性**：不支持者降级为空操作；HDD 老盘通常不支持 ⇒ 行为不变 | **只在事务提交之后**丢弃 ⇒ 崩溃语义不变 | **可直接做**（含 --no-discard 开关）✓ |
| **S3 簇默认 16 KiB** | **必须只作用于 SSD 卷**：HDD 卷默认仍是 4 KiB ⇒ 行为不变 | 分配契约不变 | **做成卷级策略**（STFS_FEATURE_* 位）✓ |
| **S4 事务合并** | ⚠️ **会改变提交粒度** ⇒ 崩溃时"丢多少"会变 | 需要**显式 opt-in**（走既有 batch 方向），**默认保持每次操作一提交** | **只做 opt-in，不改默认** ✓ |
| **S5 CRC32C 硬件路径** | 纯正收益（同结果、更快） | 校验强度不变 | **可直接做** ✓ |
| **S6 块头加"连续簇数"字段** | ⚠️ **唯一动盘上格式** ⇒ **HDD 侧也受影响** | 加性字段 + 版本/标志位；需与 80/EFI/D0 **同步** | **放最后**，且必须先门禁全绿 + 跨包同步 ✓ |

**总判**：S1/S2/S5 **不动任何既有语义**，可以放心接；S3 是"只对 SSD 卷生效的默认值"；S4 走 opt-in；
S6 是唯一真正动格式的一项 ⇒ **单独一批、单独门禁、跨包同步**，并在此之前**先用 S1 拿到实测收益**（S1 可能已经够用）。

## 7. 执行顺序（接在 HDD 真盘实测之后）

1. HDD 真盘实测收口（大文件端到端 + 段数/吞吐实测 + 报告）
2. **S1 → S2 → S5**（不动语义，一批；门禁 40/40）
3. **S3**（SSD 卷级策略；HDD 默认不变）
4. **S4**（opt-in 批次提交）
5. 视 S1 实测是否已达"≈ NTFS"判据，再决定 **S6/S7** 是否必要（**不必做就不做** ✓）
