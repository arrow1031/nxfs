## H.6 对 V1 的正确处置：吸收特性，不保留版本（人类 2026-10-04，逐字）

> **"V1可以做优秀特性吸收吞并，但是这个版本肯定是没了"**

**执行口径（Lead）**：

1. **V1 作为一个"版本"确定没了** ✓ —— 不保留读路径、不做兼容分支、不做版本共存（§H 第 1 条）。
2. **但 V1 里的"优秀特性"可以吸收吞并** ✓ —— **取其实，不存其形**：
   把值得留的设计思想**在当前单一版本里用我们自己的结构重新表达**（例如链/块组织，见 §H.5）。
3. **判据（关键，防走样）**：吸收 = **直接把可用的实现 copy 过来**（**拿现成的用，不重写** ✓；人类 2026-10-04 原话："**不重写，直接copy**"），接到**当前单一版本**上（须与当前契约对齐＝名实相符），**仍然不是**
   * 加一条"读旧 V1 卷"的路径 ✗；
   * 加兼容分支/垫片/双代号 ✗；
   * 保留旧表示（如"内嵌 `next_blk` 链"这一**形**）来省事 ✗。
   上述任一 ⇒ 属 §H.2 **屎山**，不做。
4. **具体落点**：R1「**去内嵌链 = 块层位置映射**」就是本条的范例 ——
   **"链/映射"这个思想吸收进当前格式**，而**内嵌 `next_blk` 这一表示退役**；
   于是 ①（精确重建）的缺口由"取消内嵌链"消除，**而不是**给旧链加只读面。
5. **文档义务**：吸收了什么、丢掉了什么，必须在 `FREEZE.md` 追加节与报告里**如实登记**
   （含"旧卷不再保证可读"）。

## H.5 容量侧的可为与不可为（人类 2026-10-04，逐字）

> **"容量这边我们能做链子，能做块，但是不能动逻辑最小单位和物理最小单位"**

**执行口径（Lead）**：

1. **可以做的（上层组织手段）** ✓：**链**（chain：分片链/块链/映射链）、**块**（block）等
   **聚合与组织结构** —— 表达大容量靠它们；设计自由度在这里（仍受 §H 单版本 + §H.2 反屎山约束）。
2. **不可以动的（硬件/系统给定的地基）** ✗：
   * **逻辑最小单位**（logical minimal unit，如逻辑扇区）；
   * **物理最小单位**（physical minimal unit，如物理扇区）；
   —— 二者是**客观事实**，**不得改写、不得自定、不得软动**；只能**读取并适配**
   （经系统接口取，与 §H.4 及"不要自定，让系统给值"同一约束）。
3. **判据**：任何涉及"最小单位"的代码，必须能回答"**这个值从哪个系统接口/哪条硬件事实来**"；
   凡自己定义、假设、或改写最小单位 ⇒ **违规** ✗。
4. **层级关系（一句话）**：**最小单位是地基（硬件给，不动）；链与块是楼（我们能做）**。
   簇大小夹在中间 ⇒ 由**硬件自适应**（§H.4），且须是逻辑最小单位的整数倍、并对齐物理最小单位。
5. **不放松的仍不放松**：绿闸门、名实相符、放宽四要件、一项一动、不许半成品。

## H.4 簇大小与硬件的关系（人类 2026-10-04，逐字）

> **"我们的簇大小和硬件该对还是要对上的，这种类型的大小只能自适应硬件，不能软动（自适应是留潜力，随便软动那是无视硬件设计）"**

**执行口径（Lead）**：

1. **簇大小必须与硬件对上** —— 这类"尺寸"的**唯一合法来源是硬件事实**
   （物理扇区大小 / 介质几何 / 器件特性等），且**取值须经由系统接口取得**
   （与既有裁定"**不要自定，让系统给值（哪怕是格式化也得用系统的磁盘管理）**"一致）。
2. **可以"自适应硬件"，不许"软动"** ✗：
   * **自适应 = 留潜力** ✓ —— 保留"按硬件事实推导、可分档适配不同硬件"的机制；
   * **软动 = 无视硬件设计** ✗ —— 由软件单方面拍一个数、或按与硬件无关的量（如"卷容量"单独）
     去推移簇大小，**不允许**。
3. **判据**：任何簇大小取值的改动，必须能回答"**它对应哪一条硬件事实、从哪个系统接口取的**"；
   答不上来 ⇒ 不合法 ✗。
4. **对先前表述的更正**：我此前把"**簇大小按容量自动推导**"当成 B7（u32→u64）的"更小替代方案" ——
   **该定位作废** ✗：按容量推导属"软动"。容量天花板的正解是
   ① **B7 u64 地址宽度**（结构性、已按 §H 放开做），或
   ② **硬件自适应**（更大的物理扇区/介质 ⇒ 更大的簇），**二者都不是软件旋钮**。
5. **不得外溢的仍不得外溢**：绿闸门、名实相符、放宽四要件、一项一动、不许半成品 —— 一条不放松。

## H.3 兼容的边界（人类 2026-10-04，逐字）

> **"兼容只保留对系统接口的实现和兼容，甚至这个可能还得堆工作量（开发嘛，现在费劲以后省事）"**
> **"各模块的互相兼容也得在（当前还能重构，发布之后就不好说了）"**

**执行口径（Lead）** —— **区分"接口兼容"（保留、可投入）与"数据/版本兼容"（退役、禁堆）**：

1. **保留的兼容面（两条，且是正当投入，不许按 §H.2 削减）** ✗：
   * **(a) 系统接口的实现与兼容** —— 对 OS / WDK / EFI / Linux 的 API 契约要**完整实现并保持兼容**；
     这块**可能就是要多花工作量**，属"**现在费劲、以后省事**"的投资 ✓（机械盘+多系统目标要求这条路走通）。
   * **(b) 模块间契约兼容** —— 本项目包与包之间的公开接口/契约（`stfs_meta_*` / `stfs_sp_*` / `stfs_st_*` /
     `stfs_blk_*` …）要保持**可用且一致**；**趁现在还能重构就重构干净**，重构完把契约**钉住**
     （人类原话："当前还能重构，发布之后就不好说了"）。
2. **退役的兼容面**：旧盘上格式版本（V1/V2/V3）、旧数据读路径、为兼容旧账而加的适配层/垫片
   —— 一律按 §H + §H.2 **删除收敛** ✗。
3. **判据**：任何新增的兼容代码，**先分类**：属"接口兼容(a)(b)" ⇒ 做（可投入）；
   属"数据/版本兼容" ⇒ 不做 ✗；**说不清属于哪一类 ⇒ 不做** ✗。
4. **连带收益**：包间契约**钉住**后，**库与驱动/工具解耦**（驱动只依赖公开接口）
   ⇒ 后续各模块可**独立升级**（架构裁定"各做各的 lib 模块，接口不变就能调动"）。

## H.2 开发阶段反屎山纪律（人类 2026-10-04，逐字）

> **"我们还在开发阶段为什么要堆屎山代码，堆这种东西的工作量和不稳定性都巨大"**

**执行口径（Lead）**：

1. **删除优先**：面对历史包袱 / 旧路径 / 双实现，默认动作是**删掉并收敛**，**不是**"再加一层适配" ✗。
2. **禁止堆叠**：不许新增兼容层 / 适配垫片 / 新旧双路径 / 临时开关来"掩住"旧结构；
   **不许**把"为下一批铺路"当保留理由（人类 2026-10-01 已明说它不能当豁免）。
3. **替换即替换**：确需换实现 ⇒ **一处替换、改完即删旧**，**不留"两条都能跑"的中间态**；
   迁移的中间态只允许存在于**同一批之内**并随该批收尾消失。
4. **判据**：任何改动若**增加**了长期共存的分支/路径数 ⇒ 视为**削减该项收益**，必须在报告里**单列**
   并说明为何不可避免；**说不清就改设计（删），而不是加代码** ✗。
5. **具体落点**（与 §H.1 一致）：不保留 V1/V2/V3、不做跨版本兼容矩阵、**v1 读路径退役**、
   多版本分支收敛为单一版本。
6. **不放松的仍不放松**：绿闸门（落地最低门槛）、**名实相符**、放宽四要件、一项一动可回滚、不许半成品。
7. **工作量口径随之改判**：凡"**补适配/补兼容/补垫片**"类条目 ⇒ 一律改判为"**删除 + 收敛**"，
   并按其**净减少的分支/路径/行数**计价；**净删也是成果**（在本台账里同样计入进度）。

## H. 格式与版本策略（人类 2026-10-04，逐字）

> **"地址宽度该做就做，我们不保留V1V2V3，在不完全定型的现在只有实现和改动（目前不要求对旧账兼容嘛）"**

1. **不保留 V1/V2/V3** —— 格式只维护**一个演进中的版本**：不做多版本共存、不做旧卷读路径、
   不做"跨版本兼容矩阵"这类机关。**旧账不要求兼容** ✓。
2. **但必须如实登记**"**旧卷不再保证可读**"（README/FREEZE/报告都要写）——**不许静默丢弃** ✗。
3. **B7 u32→u64 地址宽度 ⇒ 放开做**：此前"触及完全重构 ⇒ 须单列人类裁定"的顾虑**由本条解除**
   （既然不保留多版本、不要求旧账兼容，它就不再是"重构级"风险面）。
   **但仍按"一项一动"**：**地址宽度**是一项，不许把簇大小推导/尾簇打包/转义 extent 等混装进同一批 ✗。
4. **连锁退役（省下的就是收益）**：
   * `跨版本兼容矩阵-演练.md` 对应的常驻回归（`verify/` 下的 `rehearse_compat.py` 类）⇒ **退役，不实现**；
   * **v1 读路径（`next_blk` 链）** ⇒ **退役**（与 §C 的"去内嵌链 = R1 块层位置映射"方向一致）；
   * 版本兼容分支/多版本表 ⇒ 收敛为单一版本；
   * 相应地，扫描表里"兼容矩阵常驻回归""旧卷不保证可读的文档表述"等条目**由"补做"改判为"退役/改口径"**。
5. **①（精确重建）随之简化**：原先要"给 v1 数据链加只读面"，现在**v1 本身退役** ⇒ 该缺口的存在性被
   "**取消 v1**"消除，**比新增只读面更小** ⇒ 优先走取消 v1（仍须实测钉住"不再存在未被覆盖的数据链"）。
6. **"不完全定型"只意味着改动自由，不意味着质量降级** ✗：绿闸门（最低门槛）、**名实相符**、
   放宽四要件、一项一动可回滚、**不许半成品** —— **一条都不放松**。

| 层 | 目标 | 判据 |
| :-- | :--- | :--- |
| **主战场 = 机械盘（HDD）** | 数据**安全**（不坏、可恢复）、**快速**（顺寻道/顺序/预读/整理）、**易读**（可读性、工具化、可诊断） | **最高优先**：一切危及"机械盘上安全/速度/易读"的缺陷都是 P0 |
| **SSD 侧** | 做**少量兼容**即"打平甚至强过 NTFS" | **工作量小 ⇒ 就做**（省心）；判据是"便宜且有效"，不是"完备" |
| **多系统兼容** | 工作量小就做；**大则保底"跨系统之后也能用"** | ①便宜 ⇒ 做；②昂贵 ⇒ 只做**保底互操作**（把数据带得走、在别处读得出），花哨特性让路 |

### G.2 排期口径（Lead 执行）

1. **P0**：机械盘上的**安全 + 速度 + 易读**（含 70 的回收/整理/分配器、50 的日志与恢复、30 的坏道判据、驱动写路径）。
2. **P1**：**便宜且能打平 NTFS 的 SSD 兼容面**（判据：改动面小、可指认、可回滚）。
3. **P2**：**便宜的多系统兼容**（EFI 只读驱动、Linux 侧对等、格式互操作）。
4. **保底线**：贵的兼容**只保证"跨系统之后也能用"**（数据可带走、可读回），**不为完备性买单**。
5. **不买**："完全重构级"改动面（与 L3 边界一致）；"为不存在的情形付代价"（P3 判据）。

### G.3 SSD 侧的特别纪律（人类 2026-10-04 逐字）

> **"SSD侧只是不做深度优化：因为简单优化已然够用，这俩的差别没那么离谱的大。SSD那边做了的都得做好，做不好比不做更加可怕"**
> **"'做不好比不做可怕'只限于SSD侧，因为不是专门为那边设计的，其他面别拿这个话省事（也就是说SSD的优化只要开了头就必须做干净基础优化）"**

**执行口径（Lead）**：

1. **SSD 侧不做深度优化** —— 简单优化已然够用、HDD/SSD 差别没那么大 ⇒ 深度优化类的需求**一律不做**，
   不需要再逐项论证"为什么不做"。
2. **SSD 侧"做了就必须做好"** —— **基础优化一旦开头，就必须做干净**（完整、正确、过闸门、留痕），
   **不许半成品、不许降级上线**；若一批**开不了头就不开**（宁可不开，也不做一半留坑）。
3. **这条纪律不得外溢**（人类同句限定）—— **"做不好比不做可怕"只限于 SSD 侧**；
   **机械盘主战场、跨系统兼容、库层、驱动**都**不许**拿它当省事的理由 ✗。

## B. 流程纪律（血的教训，按此办）

* **子代理不提交** → **Lead 审 diff** → **Lead 提交** → **Lead 在干净树独占跑 `verify/gate_all.py`**
  → `fetch` + `merge-base --is-ancestor` 确认可快进 → `push` → `ls-remote` 复核。
  *（教训：首轮闸门红，唯一失败是 `mutate.py`「先提交/还原这些改动」——它**要求干净树**；白烧一轮 30 分钟。）*
* **禁止并发构建**（实测并发会让对抗性用例/闸门红；`tools/build` 是共享面）。
* **禁止** `git checkout -- .` / `git reset --hard` / 切分支（会**静默吃掉在飞流的未提交半成品**）。
* 推送若被代理拦：加 `NO_PROXY=github.com` 直连（git/环境变量里都没配代理，是运行环境的系统代理）。
* 交流限制：**Lead 无法 `send_message` 到普通子代理**（报 "active teammate not found"）；子代理能给 Lead 发，
  * **一次只起一个流**（人类 2026-10-04 原话："**一个流一个流的起，省一点**"）：并发成倍吃 API，且本仓实测**并发构建会互相踩** ⇒ **默认串行**；唯一例外是"纯文档面（零构建、零写面重叠）"，也要统筹先点头。
* **普通子代理对 Lead 不可寻址**（实测：`send_message` / `interrupt_agent` 一律报 `active teammate "…" not found`；`list_agents` 只见 `lead`）⇒ **起了就停不下来**，只能等它自己结束/失败/API 中断 ⇒ **起之前先想清楚**。反方向可用：**子代理能给 Lead 发消息** ✓（所以要求它在报告里写全，是唯一可靠的交付方式）。
* 反方向只能靠 ①提示词内嵌 ②写进子代理必读文件（本文件 / `决策-有状态分配器.md §8.5`）。
