## 为什么冻结

按项目决定：**NAND 相关全部已冻结**，待机械盘侧（一期）开发完成并进入可用阶段后再开启。

理由（工程上成立，不只是排期）：

1. **NAND 是纯增量功能**，核心文件系统不依赖它（设计稿 §15.5 明确"核心专利不依赖 NAND 缓存"）。
2. **它的收益是性能，不是正确性** —— 在正确性还没跑通时做性能优化，会把调试面翻倍：
   一旦出现数据不一致，你无法判断是 CoW/日志错了还是缓存层错了。
3. **它会污染多个包的边界**：设计稿把"NAND 缓存管理"写在存储抽象层职责里（§一.1），
   若现在实现，`30` 包会同时承担"介质访问"和"缓存策略"两件事，
   而后者需要 `70`/`80` 的能力——形成循环依赖。

因此当前处置：**接口位置预留，实现为空**。

## 将来解冻时的工作（存档，勿现在做）

以下内容仅作**存档**，保持设计稿 §15 的可追溯性。解冻前不要实现其中任何一项。

### 设计原则（`§15.1`）

- **NAND 是缓存，不是权威数据源**。NAND 死了，机械盘上的数据必须完好。
- **完全依赖高级驱动**：高级驱动在 NAND 上创建一个**特殊文件**作为缓存容器，
  所有缓存逻辑在用户态完成。
- **专利规避**：通过用户态实现，改变技术实施主体和场景。

### 架构定位（`§15.2`）

```
高级驱动（用户态）：元数据引擎、事务、日志
        ↕
存储抽象层：NAND 可用？→ 写入 NAND 缓存文件
            NAND 不可用？→ 直接写入机械盘日志区
        ↕
   ┌────────────┴────────────┐
   ↓                         ↓
NAND 缓存文件            机械盘
（快速写入，断电可能丢失）（权威数据源，断电安全）
```

### 工作流（`§15.3`）

**写入（NAND 可用）**：写 NAND 特殊文件 → 缓存文件元数据同步写入机械盘日志区
（记录"数据 X 在 NAND 文件偏移 Y"）→ 回报写入成功 → 后台迁移到机械盘最终位置 →
迁移完成后更新机械盘日志并回收 NAND 空间。

**写入（NAND 不可用）**：走原有路径。

**读取**：先查 NAND 缓存文件 → 没有则查机械盘。

> ⚠️ 这里有一个**将来必须解决的设计问题**：读取路径"先查 NAND"意味着
> NAND 上的条目**先于**机械盘日志生效。这与 `60` 包的"权威不对称"规则
> （目标侧权威、源侧辅证）需要对齐——NAND 条目在迁移完成前属于哪一侧？
> 解冻时必须先裁定这一点，否则会与缓存一致性机制冲突。

### 故障场景（`§15.4`）

| 场景 | 后果 | 恢复方式 |
| :--- | :--- | :--- |
| NAND 写入中断电 | NAND 数据丢失，但机械盘日志已记录 | 挂载时读机械盘日志，发现 NAND 条目无效，回滚该事务 |
| NAND 迁移中断电 | NAND 数据可能已部分写入机械盘 | 按机械盘日志决定完成或回滚 |
| NAND 盘彻底死亡 | 缓存数据全部丢失 | 标记"NAND 缓存"的条目全部失效，回滚对应事务 |
| NAND 盘移除 | 同"彻底死亡" | 挂载时检测不存在，自动降级为纯机械盘模式 |

### 专利规避设计（`§15.5` / `§17.6`）

- 用户态实现，不涉及内核文件系统或硬盘固件；
- 特殊文件容器（固定大小稀疏文件），避免"设备控制器"、"集成于 HDD 内部的 NAND"
  等硬件特征；
- 日志结构、文件系统元数据感知；
- 作为**可选功能**发布，不绑定核心。

> 注意：以上是**设计稿的主张**，不是法律结论。解冻并准备发布前应做实际的
> FTO（自由实施）检索，不能仅凭此节就认定已规避。

### 性能收益（`§15.6`，**设计稿声称值，未验证**）

| 操作 | 纯机械盘 | 加 NAND 缓存 |
| :--- | :--- | :--- |
| 4K 随机写入 | 800–1500 IOPS | **50000+ IOPS** |
| 写入延迟 | 5–15 ms | **0.1–1 ms** |
| 断电恢复 | 1–3 分钟 | 1–3 分钟（机械盘日志不变） |

> 这些数字**没有实测支撑**。解冻后若要对外引用，必须先做出可复现的基准测试，
> 否则不应写进任何对外文档（这也是 API 仓库 README 里对"比 NTFS 先进"这类
> 未验证表述的处理原则）。
